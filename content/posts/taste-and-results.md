有人问，一个产品为什么这样设计，回答是：创始人有品味。

有人问，一个 Agent 框架的能力到底怎么样，回答是：效果很好。

这两句话很容易让人产生已经得到解释的感觉。一个给出了值得信任的人，一个给出了值得期待的结果。但继续往下问，最重要的部分仍然没有出现：设计者想解决什么问题，为什么选择这个方案；框架在哪些任务上表现好，和谁比，好到什么程度，优势从哪里来。

我想批评的就是这个动作：**当一个问题需要理由、证据和条件时，用概括性的评价完成回答，并让讨论停在那里。** 赞美和批评都可能这样做。“没有品味”“效果不行”，同样可以把尚未解释的问题提前结案。

这件事值得从语言和组织两个角度看。语言解释了这些词省略了什么，组织解释了人们为什么愿意这样说、也愿意接受这样的回答。

## “品味”和“效果”分别省略了什么

先看“品味”。一个设计可能包含信息排序、交互路径、表达语气、视觉节奏，以及对用户自主性的态度。把这些选择全部归结为品味，我们就很难知道，究竟是哪一个判断值得学习。

这里还容易形成一个循环：因为产品好，所以设计者有品味；因为设计者有品味，所以产品好。两句话互相支持，却没有引入独立依据。即使我们有其他作品证明这个人的判断值得信任，信任也只能帮助决定是否采纳建议，无法自动补全这一次选择的理由。

讨论“设计初衷”时，问题更明显。一个成品能让我们观察到布局、交互和实际体验，但作者当初为什么这样做，需要设计记录、访谈、早期方案等材料。我们可以推测某个安排有利于连续阅读，也可以欣赏它的克制；仅凭这些，还无法断言设计者的初衷就是保护注意力。

**创作者的实际动机、方案可以成立的理由、方案最终产生的结果，是三个需要分别说明的问题。** 一个方案可能因实现成本低而被采用，后来产生了不错的体验；一个初衷很好的设计，也可能没有实现预期。

再看“效果”。“这个框架效果好”可能意味着任务完成率高，也可能意味着演示流畅、回复好看、人工接管少，或者开发者很快就能接入工具。它把多个评价维度放在同一个词里，连被评价的是运行表现还是开发体验，都可能没有说清楚。

对于框架，还有一层归因问题。我们看到的是模型、提示词、工具、数据、运行环境和框架共同产生的结果。如果同时换了模型、增加了重试、重写了工具描述，结果变好以后，框架应当分到多少功劳？一句“效果好”回答不了这个问题。

这两个词省略的内容并不完全相同。“品味”容易把决策过程归结为人的某种能力，“效果”容易把有条件的系统表现概括成整体优势。它们共同造成的问题是：听者拿到了结论，却拿不到足以理解和使用结论的依据。

## 语言可以省略，解释需要补全

语言学里，边界模糊、词义歧义和信息省略是相关但不同的问题。“多快算快”涉及边界，“效果”具体指什么涉及评价维度，“和谁相比”没有说出来涉及语境补全。讨论这些表达时，笼统说它们“太抽象”，还没有定位问题。

“好”尤其容易掩盖多维评价。一个方案可以更快、更贵、更稳定，也更难维护。我们说它好，往往已经在心里给这些维度排了优先级。关于多维形容词的语义研究也讨论了类似问题：判断取决于哪些维度被纳入，以及这些维度如何组合。把这个视角用于产品讨论，可以发现，争论双方有时连正在使用什么标准都不一致。[相关语义研究：Avoiding predicate whiplash](https://journals.linguisticsociety.org/proceedings/index.php/SALT/article/download/2628/2376/0)

不过，要求所有人每句话都交代完整条件，也不合理。

Grice 的合作原则要求说话提供当前交流目的所需的信息，同时避免提供过量信息。两个人刚看完同一份测试报告，其中一个说“这次效果不错”，完全可能已经足够。问题出现在一个人要求了解选型理由，另一个人仍然只重复这句话。[Grice，1975](https://projects.illc.uva.nl/inquisitivesemantics/assets/files/papers/Grice1975.pdf)

Piantadosi、Tily 和 Gibson 关于语言歧义的研究提出，在语境能够帮助确定含义时，歧义可以提高沟通效率。这项研究处理的是语言歧义，不能直接替某一句职场评价辩护；它提醒我们，省略与多义本身都有正常的沟通功能。[Piantadosi 等，2012](https://colala.berkeley.edu/papers/piantadosi2012communicative.pdf)

因此，我更愿意用这个标准判断一句话是否说够了：**听者能否借助已经共享的信息，理解这个判断，并完成眼前的任务。** 表达欣赏、请求解释、比较方案和决定投入，各自需要的信息不同。

听者已经追问“具体好在哪里”，就说明共同语境还不够。此时继续说“这是品味，你得自己体会”，实际上把解释任务留给了对方。如果对方还因此被认定为不懂产品，理解上的缺口就进一步变成了身份上的差距。

## 为什么这种说法会流行

现有研究提供了几种有用的解释路径。它们研究的对象包括语言理解、人际判断和组织沟通，并没有共同完成一项针对中文产品评审中“品味”“效果”用法的调查。下面涉及具体职场情境的部分，是据此作出的分析，不能用来直接诊断某个人的动机。

### 感觉先出现，解释还没有形成

人有时确实先感觉到某个方案不对，过一会儿才说得出问题在哪里。把这个阶段的判断当作线索，是合理的。

Kahneman 和 Klein 对专业直觉的讨论指出，判断直觉是否可靠，需要考虑环境是否存在可学习的规律，以及判断者是否有机会通过反馈学会这些规律。确信自己看得准，不能单独证明判断准确。[Kahneman 与 Klein，2009](https://pubmed.ncbi.nlm.nih.gov/19739881/)

所以，“我现在还说不全，但这两个页面让我觉得节奏不同，我们放在一起看看”，可以成为有价值的开场。经验有机会通过对照、示范和修改逐渐展开。要求对方当场给出完整理论，可能反而丢掉有用的线索。

另一个可能是，说话者高估了自己的理解。Rozenblit 和 Keil 在关于解释性知识的实验中发现，人们常以为自己理解复杂机制，直到被要求详细说明，才意识到知识缺口。这被称为“解释深度错觉”。原研究不能直接证明某个产品判断浅薄，但它提示我们：觉得自己懂了，与能够解释清楚，可能存在距离。[Rozenblit 与 Keil，2002](https://doi.org/10.1207/s15516709cog2605_1)

这两种情况表面上都可能说不清楚。实际交流中，更有用的观察是：对方是否愿意继续指认实例、比较方案、修正判断。单凭一次停顿或一个大词，很难区分经验尚未展开和思考尚未完成。

### 模糊让不同的人暂时同意

“我们要做有品味的产品”“选效果最好的框架”，很容易获得同意。设计师可能想到视觉表达，工程师可能想到稳定性，负责人可能想到商业演示。大家在同一句话上达成一致，却未必共享同一个目标。

Eisenberg 的策略性模糊理论强调，组织沟通同时服务于多个目标。保留多种解释，可以容纳差异、支持组织变化，也可能维护既有优势地位。模糊有时能够帮助合作持续进行。[Eisenberg，1984](https://www.tandfonline.com/doi/10.1080/03637758409390197)

从这个视角看，提出方向时保留一些空间可以理解。但进入方案选择、资源投入或交付验收之后，相关标准就需要展开。否则，表面共识掩盖的分歧会在执行中重新出现：做的人以为已经完成，验收的人觉得“还是不对”。

这也是一种成本转移。前面省下的解释，可能变成后面的返工、猜测和反复揣摩。

### 抽象评价也在传递地位

Wakslak、Smith 和 Han 的七项实验发现，在所研究的情境中，使用更抽象语言的人会被参与者感知为更有权力。作者认为，这与抽象表达传递出的判断姿态和思维方式有关。研究涉及的是权力感知，不能据此推断抽象说话的人更有能力，或一定想操纵他人。[Wakslak 等，2014](https://pubmed.ncbi.nlm.nih.gov/24956313/)

这个结果为职场中的一种现象提供了理解角度：一句整体评价可能让人显得站得高、看得全，而要求展开细节的人反倒显得没有领会。

当评审允许某个人用“没品味”否决方案，却要求其他人提交完整证据来反驳，双方承担的论证责任就不对等。判断这种问题，需要看具体互动：谁可以不说明依据，谁必须不断自证，标准是否在追问后改变。

这比仅凭“品味”两个字，就断言对方在炫耀身份或滥用权力，要扎实得多。

### 模糊有时在保护关系，也可能保护说话者

Brown 和 Levinson 的礼貌理论把许多间接、弱化的表达放在面子管理中理解。人们说话时，也在处理对方是否受冒犯、关系是否还能维持等问题。[Brown 与 Levinson，1987](https://www.cambridge.org/highereducation/books/politeness/89113EE2FB4A1D254D4A8D2011E542E4/realizations-of-politeness-strategies-in-language/C6520CBC91390F462B85F1D967BBD809)

但“含糊”并不保证“温和”。“你这个东西没有品味”可能让对方怀疑自己的整体能力；“这个弹窗遮住了我正在填写的内容”虽然具体，却给出了可以共同处理的问题。

还需要考虑说清楚之后的风险。说出一个具体预期，就留下了日后核对的依据。如果承认不确定会被视为能力不足，修改判断会被当作出错证据，人就可能倾向于保留解释空间。这是关于组织激励的推论，不能简单写成所有人的共同动机。

相关研究也提醒我们，增加追责压力未必自动改善思考。Lerner 和 Tetlock 的综述指出，问责的影响取决于具体规则；在某些条件下，人会更仔细地推敲判断，在另一些条件下，也会迎合听众或为已有立场辩护。[Lerner 与 Tetlock，1999](https://pubmed.ncbi.nlm.nih.gov/10087938/)

因此，如果一个团队想让人说得更具体，就要能接受“这是初步观察”“我还没有排除另一个原因”“这个证据让我改变了看法”。否则，要求解释可能只会增加一层事后编出的理由。

## 错误发生在评价承担了它无法完成的任务时

我认为最值得批评的有三种情况。

第一，**把评价当作原因。** “有品味”概括了对人的认可，却没有说明目标如何影响方案；“效果好”概括了结果，却没有解释哪个机制带来了收益。

第二，**把局部观察扩展成整体能力。** 某个演示成功，能够证明那个案例在当时条件下跑通；要进一步说明框架适合长期使用，还需要覆盖任务、重复运行、失败情况和成本。一个视觉风格受到赞赏，也不意味着它适合所有产品目标。

第三，**让标准始终无法被共同检查。** 一开始说关心效率，方案改善效率后又说缺少气质；要求证明效果，拿到结果后又改用另一套任务判定。标准可以随着理解加深而调整，但变化需要被说出来，也需要说明理由。

这些问题会妨碍学习。参与者不知道下一步应该改变哪个对象，也不知道分歧来自观察、目标、推理还是价值排序。成功难以复用，失败难以定位。

不过，说明问题也不等于把一切变成数字。审美选择、品牌立场和价值排序可以通过作品比较、具体形式、使用情境和代价来讨论。经验断言需要证据，价值选择需要交代理由。要求所有判断都接受同一种“证伪”，会把不同问题混在一起。

“我们愿意让页面更安静，即使少展示一些推荐内容”，已经表达了一个可以讨论的取舍。接下来需要检验的是这种安排是否实现目标，以及团队是否接受它的代价。

## 解释设计：把选择放回问题和取舍里

设计说明可以从五件事开始：为谁、解决什么问题、有哪些可选方案、为什么选这个、接受什么代价。

这与设计研究中的 QOC 方法相通：用问题、选项和评价标准组织设计理由。它帮助人们比较可能方案，呈现选择依据。这样的分析也可以事后进行，因此它本身不能证明设计者当时就是按这条路径思考的。[MacLean 等，1991](https://www.researchgate.net/publication/233367028_Questions_Options_and_Criteria_Elements_of_Design_Space_Analysis)

下面是一个虚构的阅读产品示例：

> 这个页面优先支持已经开始阅读的人连续读完一篇文章。我们比较了侧边栏推荐和文末推荐两个方案，选择把推荐放到文末，让正文区域减少竞争性入口。代价是阅读过程中发现其他内容的机会减少。这个方案能否减少非预期的跳出，需要结合阅读过程观察和用户反馈继续判断。

这段说明暴露了几处可以讨论的地方：目标人群选得对不对，推荐是否真的构成干扰，减少发现机会是否值得。团队能据此决定下一步看什么。

如果我们只是在分析别人的产品，表达就应该换一个位置：

> 页面把推荐放到了文末。我推测这有利于保持正文区域的注意力集中，也欣赏这种安排。不过，目前没有找到设计者说明初衷的材料。

如果讨论的主要是审美，也可以具体：

> 我更喜欢第二版。它减少了字号层级，标题和插图的关系更接近我们选定的参考作品，整体语气更安静。代价是强调程度降低。我们需要确认这种气质是否适合这次希望传达的内容。

这里没有强行给“安静”打分，但判断已经有了对象、参照和范围。对方可以拿出另一个版本，指出不同的形式关系，或质疑品牌目标。审美经验也由此变得可以分享。

具体说明不必一次完成。如果暂时只有直觉，就先标明是初步判断，用样例和对照推动下一步。等到需要共同决定时，再把关键理由补齐。

## 评价框架：让结论停在证据能到达的地方

评价 Agent 框架，首先要明确正在比较哪种价值：完成任务的能力、运行中的可靠性，还是接入、调试和维护的便利程度。框架可以在其中一方面有价值，同时在另一方面没有明显优势。

对于任务表现，《AI Agents That Matter》指出，忽略成本、缺少充分的简单基线、测试集隔离不足和评测不标准，会影响我们对性能与性能来源的判断。这意味着，分数上涨之后仍然需要核查比较条件。[Kapoor 等，2024](https://arxiv.org/abs/2407.01502)

日常选型不必一开始就做成大型 benchmark，但至少应交代以下内容：

| 要说明的问题 | 可以提供的材料 |
| --- | --- |
| 准备用它做什么 | 任务来源、主要类型、难度和重要约束 |
| 怎样判断好坏 | 成功条件、失败判定；开放产物则给出评分标准和示例 |
| 在比较什么 | 模型、提示词、工具、框架版本与各自配置 |
| 观察到了什么 | 样本数量、每题运行次数、分类型结果和失败案例 |
| 为结果付出什么 | 费用、耗时、重试次数和人工介入 |
| 结论能支持什么 | 系统选型、具体机制的贡献，或尚待验证的猜测 |

例如，要检查中断后的恢复能力，可以先做一个范围明确的实验。下面同样是虚构示例：

> 我们选取需要跨步骤保存状态的任务，在预设节点注入中断，再检查恢复后能否继续完成任务、是否重复执行已完成的写入。两个实现使用相同模型版本、工具权限和预算，记录各题多次运行的结果、额外耗时和费用。当前比较支持这两套配置在这些恢复场景下的表现差异；检查点机制贡献了多少，还需要补充开关该机制的对照。

有些框架无法在完全相同的配置下工作，也可以比较各自合理调优后的实现。此时要把调优投入和配置差异说出来，并把结论限定在两套系统的选型价值上。若进一步声称某个机制导致提升，就需要能隔离该机制影响的证据。

重复运行也要区分问题。τ-bench 区分了 `pass@k` 与 `pass^k`：前者关注同一任务的 k 次试验中至少成功一次的概率，后者关注 k 次全部成功的概率，并在任务间取平均。一个偏向多次尝试找到解的能力，一个偏向反复执行的可靠性；两者需要结合使用场景解释。[Yao 等，2024](https://arxiv.org/abs/2406.12045)

看到成功率差异，也应交代样本规模和波动。对同一小批题反复运行，主要帮助了解这些题上的稳定性，无法自动扩大结论覆盖的任务范围。对测试题反复调优后，还需要保留未参与调优的任务来检查结论。

对于开发体验，则可以记录完成同一个接入任务需要哪些步骤、定位一次失败需要哪些信息、修改业务流程影响哪些代码。把体验展开为场景和材料，也比一句“开发者体验好”更容易比较。

解释机制当然有帮助，但机制故事本身也需要验证。暂时不知道为什么，依然可以报告一个条件清楚、重复观察到的结果；有一套听起来合理的解释，也不能直接宣称它在新任务上有效。

## 让说清楚成为一种可以承担的工作

在会议里，最实用的起点可能只有三个问题：

> 你具体指哪个现象？
>

它们可以把“缺少品味”展开成一个方案对照，把“效果不好”展开成一条失败轨迹。遇到“我暂时说不全”，可以约定先拿例子，再补判断；遇到价值分歧，可以直接讨论优先级和由谁决定。

组织也要为这种表达提供条件。Edmondson 对 51 个工作团队的研究发现，团队心理安全感与学习行为相关。它支持我们重视提问、承认错误和寻求反馈的环境，但不能据此承诺某一套提问模板必然改善团队。[Edmondson，1999](https://dash.harvard.edu/entities/publication/13a7b031-0fdd-45ec-a7e0-2b80e2bc679f)

我的建议是，要求说明依据，同时允许依据暂时不完整；记录判断，也记录当时的不确定性；回顾结果时检查哪些假设需要更新。决策者同样承担解释责任。最终需要有人拍板时，可以明确说这是当前目标下的取舍，并写下愿意承担的代价。

“品味”和“效果”可以留在交流里。它们适合概括已经展开过的判断，也可以提示一个值得继续追问的方向。

我希望减少的是那些停在标签上的解释。讨论设计初衷，就把目标、选择和理由讲出来；讨论框架能力，就把任务、条件、结果和归因边界讲出来。这样，一次评价才能成为别人能够理解、检验、争论和继续工作的材料。
