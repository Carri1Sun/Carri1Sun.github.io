### 我们先给 Agent 评测下一个定义。

评测也是测，评测就是一个测试工作。

跟软件测试工作相比，模型以及 Agent 这些东西迭代的时候，改动的不确定非常强，有些东西不是说你做了逻辑 A，就一定能产出逻辑 B，具体有两方面的不确定性：

1. 它依赖模型的随机输出。
2. Agent 是一个内部耦合性很强的系统，并且他的内部复杂程度跟模型的随机性之间还是在做一个乘法，你在改一个东西的时候，比如你改了第一句 prompt，可能就会对最后一句 prompt 所要求的有影响。这个 Prompt 写的比较多的人应该都有感受，你在 comfy 里面用生图的时候，想搞出一个效果，很多时候要求你对每一个关键词都有很精细的了解。

这对人来说是比较黑盒的。虽然它有一定程度的对应关系，相比于训练模型也有一定程度的可控性（现在看可能跟现在的专项数据优化的路径差不多了），但让人把它的逻辑完全梳理清楚，是一件太困难的事情，对人的要求非常高。所以评测从正常软件开发里的测试里分化出来了，并且相比于后者，他的重要性也被提了上来。

由此引伸出来的问题是，Agent 评测和模型评测有什么区别

### Agent 评测和模型评测的区别

在 Agent 或者模型工作内部，评测工作往往跟迭代深度绑定，两者放在一起，改进手段和评测目标往往是同源的，会形成同时做裁判和选手的局面。

而对于模型公司来说，在很多能力的迭代上采用跟评测集设计灵感同源的训练集并不是问题，现有训练范式正是在确保这样也能做出效果，放到用户手里也能 work。

相比之下，大部分 Agent Harness 迭代是工程手段工作，并没有哪种工程范式可以做这样的保证。

有句古话叫压缩即智能，为了刷榜/满足评测维度要求服务的训练也存在数据的压缩，多少也有智能，但是 harness 工作是 decompression 或者 steer，decompression 还谈得上对智能的释放，但很多评测是通过 steer 完全可以满足的，steer 在一些程度上就相当于作弊了。

举个例子，我定了一个评测指标是要求 Agent 搜索的时候要尽可能全面，工程老师在 systemprompt ⾥写 ⼀句"没搜到⼆⼗个结果就重试直到搜够"，分数⽴刻上去，但是实际使用的时候未必是个好的体验。

那么到实际的团队协作方式去看，Agent 的评测和迭代工作就没法像模型团队那样分工，很多模型训练任务可以从评测出发，评测在整个流程里被视为灵感的起源，Agent 完全无法复刻这条路径。

如果真的团队里独立出来一个比较大的评测团队，它能做的事情主要也就是用于防退化的约束，定位问题在模型还是⼯具还是 context 的归因，把⼈在看 agent 的运行路径和产物时浮现出的判断灵感变成可以重复使用的校准。

给上述观点一个结论：模型评测只定义问题，Agent 评测同时要定义解决⽅案，难度更高

## Agent 评测实践经验分享

实践上，这个工作有很多工程范式，现有资料里面我觉得看这个比较好

https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents

评测的设计涉及两个角度：

1. 第一部分是比较产品角度的，非技术人士和用户关心的非常多的：怎么样设计题目以及打分机制
2. 第二部分是工程角度的事情：Infra 应该怎么设计。

工程角度原文有很充分的介绍，接下来主要讨论题目和评分的设计。这里分成两部分：先看公开的 bench 怎么设计和迭代，再分享内部围绕产品迭代做评测时遇到的难点以及积累的解决经验。

### 公开的 bench 如何设计和迭代

我们先看看公开的 bench 是怎么做的，比如 Terminal-Bench，从 1.0 一直改到 4.0，这里面有个挺值得讨论的事情，就是评测本身也一直在出问题。你给 Agent 一道题，它没做出来，这个时候你得先搞清楚，到底是它能力不行，还是你这道题有问题。

先看它最开始怎么出题。[1.0](https://www.tbench.ai/news/announcement) 的思路很好理解，就是找一些需要用终端完成的工作，比如配置网络、处理数据、做科学计算，把环境用 Docker 搭起来，再给一个任务要求，让 Agent 进去做。出题的人还要提供一个验证过的解法，证明这道题确实能做出来，然后写测试去判断 Agent 最后有没有完成。

比如有道题叫 [new-encrypt-command](https://hub.harborframework.com/tasks/terminal-bench/new-encrypt-command)，给 Agent 一个自定义的加密命令行工具，让它自己看说明去完成任务。官方展示的运行里面，Agent 会先用 `--help` 看这个工具怎么用，然后再去操作。这个题我觉得就很直观，你给它一个没见过的工具，它能不能自己去读说明，把事情做完。

还有一道 [raman-fitting](https://hub.harborframework.com/tasks/terminal-bench/raman-fitting)，给它一份拉曼光谱的数据，让它把里面两个峰拟合出来，把参数写到 JSON 文件里。这里有个细节，数据给的是波长，处理的时候需要先转换成波数。官方最初展示的失败案例里面，Agent 没有处理好这个单位问题，拟合程序跑完了，但是算出来的参数没有意义，它自己还觉得已经做过检查了。

那这道题怎么打分？测试会去读它交付的 JSON，检查峰的位置、宽度这些参数有没有落在允许的误差范围里。这个例子就能看出为什么要把任务跑到底：程序能跑完、文件能写出来，后面还有一个问题，就是算出来的东西到底对不对。你只看它的回复，它可能讲得挺像那么回事，真去检查产物才能看到问题。

这里面其实已经有很多要考虑的东西了。你要测什么能力，拿什么任务来测，环境给成什么样，怎么判断做完了，每一件事情都可能影响最后的分数。比如 1.0 里面有个下载 YouTube 视频的任务，YouTube 的反爬机制一直在变，今天能跑的解法，明天可能就跑不了了。那你明天测出来分数掉了，能说明 Agent 退化了吗？这个时候就很难说了。

所以到了 [2.0](https://www.tbench.ai/news/announcement-2-0)，一方面模型变强了，需要更难的题目，另一方面也花了很多人工和模型辅助的工作去检查题目本身。后来 [2.1](https://www.tbench.ai/news/terminal-bench-2-1) 又修了 89 道题里面的 28 道，比如有道叫 `query-optimize` 的题，要求用 PostgreSQL，测试却按 Spark SQL 的输出检查。还有些题是资源给得不够，或者外部依赖变了。这些问题如果不去看具体的运行过程，最后摆出来也就是一个失败，你很容易把它算到模型能力头上。

然后还有一个问题，就是模型越来越强，原来那些题大家都能做了，那这个 bench 还能告诉我们多少东西？到了 [3.0](https://www.tbench.ai/news/terminal-bench-3-0)，他们又把任务的范围往外扩，加入更多类型的工作，更长的任务，以及多容器网络、GPU 这些更复杂的环境。出题的时候也会让专家和不同的 Agent 去看，要求有没有说清楚，测试和要求是不是一致，有没有办法钻测试的空子。这些东西都得实际跑起来才能发现。

从这个版本开始，他们也明确要持续维护这个 bench，发现问题就修，缺什么任务再加什么任务。这个事情我觉得很好理解，Agent 一直在变，环境一直在变，我们对什么工作值得测的理解也在变，那评测怎么可能出完一套题就一直不动了。

再看 [4.0](https://www.tbench.ai/news/terminal-bench-4-0)，很大一部分工作是在重新看资源给得合不合适，比如 CPU、内存、时间，Agent 的超时上限统一调到了 8 小时。另外移除了 8 道题，修了 19 道题，被移除的里面有些是大家已经都能做出来了，有些是有公开解法，或者还存在质量和兼容性问题。

回头看前面这些题，加密工具那道题里你想看它能不能学会用工具，光谱那道题里你想看它能不能正确处理数据，SQL 那道题里你还得先保证自己写的要求和测试对得上。到了运行的时候，光是时间和机器资源，就又可能让你对 Agent 能力的判断发生变化。它知道怎么做，但是你没给够时间，跟它完全不知道怎么做，最后都可能是零分。那这个零分对于你理解它的能力，到底有多大的帮助？所以看分数还得看版本和运行条件，题目和环境都变了，两个分数也就不能直接放在一起看涨跌。

从 Terminal-Bench 这几次迭代去看，做公开评测有相当一部分工作是在反复检查自己出的题：这个任务还有没有代表性，能不能区分现在这些模型，失败的原因到底是什么。评测本身也是一个需要不断运行、观察和修改的东西。

### 内部围绕迭代的评测设计

那么回到我们自己做 Agent 的团队里面，除了看它在公开的 bench 上能拿多少分，还有很多更具体的问题。比如我改了一句 prompt，想让它搜索更全面一点，实际有没有变好？会不会搜得多了，但是交付变慢了，或者搜了一堆跟用户没什么关系的东西？这些判断都得回到我们自己的产品想做成什么样，以及用户到底需要什么上面来。

接下来分享一下围绕这些问题做内部评测时，我自己的一些经验。

题目和评分的设计是个产品问题。

在一套评测基建里面，原文有定义以下两个部分：

> - A **task** (a.k.a **problem** or **test case**) is a single test with defined inputs and success criteria.
> - A **grader** is logic that scores some aspect of the agent’s performance. A task can have multiple graders, each containing multiple assertions (sometimes called **checks**)**.**

这两个东西是一个 bench 设计的时候最核心的部分，我们提到一个 bench 的时候，一般也就是在提这两个东西，在样子上是很好理解的。它一般的组织形式就是：有若干个题目（Task）；每个题目里面有若干个评测维度，并通过评分器（Grader）进行评分。

这些评分器有公用的，比如同样是设计 PPT 和设计网页，可能都会用到视觉相关的评分器去给出意见；也可能有专用的，比如设计一道题，题目是计算 6 个宝可梦在进化前和进化后尾巴数量会有多少区别，那么会给这套题写一个专用脚本判断 Agent 最后回答的那个数字是否正确。（这道题出自 GAIA Benchmark）

题目和评分的设计是产品设计，你的产品需要表现成什么样子，题目和评分就要设计成什么样子。

比如说，你希望你的 PPT Agent 在设计PPT的时候，视觉上能表现出一个特征：假如你的PPT是介绍一个麦当劳汉堡的，麦当劳的主题色是黄色和红色，那这个 PPT 也最好设计成黄色和红色。

这里我有四条主要经验：

#### 先确定评测维度再确定题目

我观察到很多人在做评测集的时候，习惯性做的事情是一上来就直接开始想题目。然后就陷入一种非常抓瞎的状态，这个时候往往会纠结这个题目是不是不太合适？这题目能不能体现出我要表现出的产品能力？以及各种类似的纠结。

这个事情的原因是，设计Agent产品的时候，我们知道，我们要处理的用户任务是不可枚举的，它里面可能有些高频、有些低频，不同的任务之间也会有组合，组合的时候会有先后顺序，并且用户完全是自然语言输入。总之，我们不可能把用户所有处理任务都枚举出来，用这些任务去代表我们的产品就提供这些能力，这是不可能的。

如果跨过评分指标的设计直接去尝试设计题目，这题目其实跟你的产品设计目标之间总会存在一些 gap，所以从我们的产品想呈现出什么样的东西，也就是我们对好坏的判断这个角度出发，先设计好打分机制，再去设计题目。然后可能每个题目再设计一些更具体的、针对这道题的打分。这可能是一个我自己用下来更好的流程。

我们可以捞一堆用户的反馈起来看，这些里面有哪些共性，比如对于设计类的任务，用户往往都反馈希望设计出来的东西符合某些标准，那就根据这个标准定义一个评测维度，比如你可以定义一个评测维度，输入一个做介绍一个物品类的 ppt，然后打分标准之一是，ppt 的主题色是否和所介绍的物品的主题色差不多。

我们也可以从你生活中见到的各种理论里面提取，比如鼎鼎大名的 manus 发的从语言学中理解出的“隐喻率”，然后可以直接根据这个客观道理去定评测维度，比如一篇调研报告里使用隐喻的地方共有多少处统计一下。或者直接定义好我们要的产品特性，比如我要设计一个做设计的Agent，那我对我的产品的定义一定是：我要设计比较好看的动效；如果是一个有流程的东西，我的动效在这里面要做到特别强，还是做到不喧宾夺主；我的用色应该是什么样的。

然后再根据这些去确定好的去设计或者把用户的反馈固化成题目，我们会发现确定了这些指标之后，设计具体的题目会发现容易很多。

#### Observability （可观测性）是评测工作里最重要的部分

围绕大语言模型的工作很多时候非常像是一门实践学科，可观测性（Observability）是实践学科中最重要的实验设计原则之一。 尤其对于那些依赖反复试验、反馈和迭代来积累知识的学科，可观测性几乎是实验能够产生有效知识的前提。

我们设想一个最极端的评测设计，先不确认任何指标，我只把结果拿出来铺出来，比如最后产出的结果、结果的截图、录屏视频；我的所有设计目标都服务于把产出的结果尽可能方便地展示给受众，可能包括：

1. 它做了一个前端，有截图预览和完整的交互预览。
2. 它做了一个视频，有一个录屏预览。
3. 它的路径，他每一步行动 summary。
4. 它用了多少时间，它用了多少 token，用的什么 effort，加载了哪些 skill。
5. 它基于哪个 harness。
6. 以及还有其他能想到的各种要素。

那么，其实观测者不需要我给他指导，他依靠自己的主观喜好直接去看也可以给出一个对于哪个结果好那个结果坏的判断。然后观测者再把自己的主观喜好梳理清楚，那就能设计出来一个更可靠的评测维度。

#### 接受定义评测维度时的主观性并且为之负责

前面说了要先确定评测维度，但是 Agent 作为一个刚刚诞生的技术产品，大家都还搞不清楚该提供何种服务，都还在围着用户问你们都用 Agent 做什么，那么从用户需求角度来看评测维度就是非常难确定的。

我们这里讨论一下“主观”和“客观”的区别，我的个人观点是，任何道理任何规律刚刚诞生的都是后都是“主观定义”，“客观标准”也都是经历了长久的时间时候形成共识或者使用某些实验或者推断证明其有效的“主观定义”。

但 Agent 这个技术和产品都刚诞生没多久，很多定义没有被大量的使用检验过，难以形成共识，另外，Agent 评测还需要评测轨迹，评测针对任务的某个中间步骤中 agent 的运作方式等等大量并不直接跟用户需求相关的东西，这些更难以寻找确切的标准。所以我们要接受自己去做一些主观的判断，并且为之负责。

在摸索的过程中，评测可以作为描述自己对产品和整体架构认知的核心手段，作为 harness 核心维护者，脑子里要尽可能了解自己的系统是怎么运行的，在什么样的条件下会有什么样的行为，评测就是这些行为的具象化。

#### 动态性比较强的 Task

举个例子，比如说我让他去帮我check每天国际政治新闻出了哪些大事儿，这样，然后他每天搜出来的东西可能都不一样。但是，我的一个一valuation可能跑在两个不同的天，就是我没法儿把搜索的这个环境固定下来

这个 Task 的评测有两个问题，一个是没办法常规意义上进行完成与否的校验，另一个是不稳定，每一天的搜索结果可能不一样。

有两种手段可以进行这种问题的评测，第一种是为了实验稳定性以及公平，可以考虑构建一个 internet archive + search 的基建来进行评测，在迭代细节的时候使用。第二种我认为可以在设计题目的时候将环境的动态性考虑进来，然后以暴露问题为目的定义评测维度，这种是可以考虑用来每天日常运行，方便观测和暴露问题的，寻找迭代灵感的。

比如，我可以设计一个这样的评测题目：

我们的题目设计为让 Agent 去搜集 50 个国际大事新闻。然后校验标准设计为，我们通过脚本或者 API 的形式去抓 100 个新闻网站的当天的新闻列表，比如什么路透社，FT，BBC。

然后再结合这两份数据定义评测维度，比如：

1. 我去判断一下这 50 个国际大事，在多少个新闻网站里出现过。代表它抓的准确性或者权威性什么之类的。
2. 有多少个没有在新闻网站里出现过。代表它挖小道消息的能力。

现在大部分用户的 Task 实际都有比较强的动态性（甚至绝大部分都依赖搜索，但根据用户要求的产出形式不同以及调研领域的新闻时效性差异，对用户实际的使用感受影响也都不同），对于强动态性的任务，要有快照这种服务于对定义好的 capability 进行 regression 的方案，同时也要建立基于真实世界的评测维度来服务于发现迭代灵感的。

## Harness 会不会被模型能力吃掉

模型能力不够强的时候，要不要靠工程问题先来兜一部分？对于比较前沿的 Agent 开发者来说，这是一个讨论的很久的问题。

这个问题我个人有以下几个观点：

1. 技术上大家的理解不会差太多，但是产品角度，一方面是产品总是要解决最后一公里问题，提供确定性的价值，另一方面很多商业决策都有个时不我待的问题，如果依赖模型的迭代来让让 Agent 变得更好，不论是等待前沿模型更新还是自己根据需求做后训练，迭代周期都太长，工程（harness）改动的最快几个小时就能完成一轮从定义好问题到改动完成到上限验证。模型真发展好了，删了也不心疼，甚至你还可以把这个东西卖给模型帮模型发展。
2. 大量 harness 本身就是由模型训练塑造的，现在的 harness engineering 工作就是 trajectory rl  这条训练路径的产物。

#### 跟模型打交道的 Mindset

我们前面把评测当成一个独立的概念讲了很多，现在社媒上不断冒出来各种独立的概念：prompt engineer、context engineer、harness engineering 等等各种新奇的功底。

我觉得他们每一个词确实有独立代表一些思想，但它们之间的交叉也非常多。

创造概念就是在创造抽象层级，好的抽象可以降低协作成本，所以造词儿这个事儿也不是个坏事，这是提升生产力必须要有的流程，不然程序员们估计还在写汇编语言。 

但坏的地方在于，市场太热的时候从业者们会急着造词争夺话语权，大家创造出来的大部分概念完全不具备一层好的抽象应该符合的基本要素，像 skill，agent，harness 这些东西到底是个啥也说不清楚，较真的用户和从业者们遇上了也一头雾水，本来是一个应该造福大家的事情，最后实际产生的作用也只有 FOMO 老板，然后老板们折腾下面的人。

评测也好，harness engineering 等词也好，所有围绕模型的工作，还是记住最终的核心目的——让 AI 表现出符合自己设计目标的效果。

#### 直接抄一个Harness不行吗？

最狭义的 Harness 直就是让 Agent Loop 能正确的跑起来和终止，再加上一些加载 skill，扩展 tool 等能力，这个部分里面的实现工作量并不大，搭一个并没有多大难度，或者直接基于 pi 或者 claude 或者 openai 的 agent sdk 封装甚至把一个已经跑的还不错的 agent 拷贝下来去魔改，这都不是很困难的事情。

但实际业务跑起来的时候，你会收到用户各种各样的反馈，每个人都会对 Agent 有各种效果上的要求。抄了之后，你得懂里面有什么，还得懂怎么改，又得有评测。不可能抄过来就完全不变了。

所以抄一个 Agent 框架内核解决不了这个问题。

evals 和 harness 设计在上一代的工作中的策略产品设计工作最类似，出题出指标就是把脑子里对于什么是好的给呈现出来，

这个东西的最好尝试和做产品是一样的，就是先跑起来在说，很多效果优化项拍脑袋拍不出来，跑一遍看看效果才能想得出来哪儿好哪儿不好，才能发现出题，定指标和设计打分机制的灵感来源。

目前看到的唯一解就是有一个人了解模型+了解模型落地+了解产品+非常又责任心的超级大哥抱着享受探索未知领域的 mindset 去全盘负责这个事情。

搭个 agent 没多少代码量和 prompt 量，但是这个工程里面堪称每一个字符彼此之间都存在耦合，对工程师负责程度和全局最优解的思考程度要求摧毁了并不追求极致的团队的分工体系。

可想而知目前没有几个团队做得好这个事情。这不是人力/钱角度的难，这是一个伟大的为人类进步探索未知的任务！

## 用户和传播角度的评测

除了专业的评测设计，还有一个话题我认为尤为重要，就是用户视角的评测，具体分为两个部分，一个是用户怎么样理解一个模型或者一个 harness 的能力以及表现出某种倾向性的原因，另一个是用户怎么看待现有的各种评测分数。

#### 现有广泛传播的评测的问题

现在大部分人，不只是用户，甚至包括专业从业者，也没有时间专门测试一个模型的表现。人们能看到的模型效果展示非常鱼龙混杂。

现在能接触到的 bench 分两部分。

第一部分是专业的 benchmark，每个模型发布的时候都会跑，有配套论文，他们在设立的时候定了很多指标，再通过一些论证去证明它合理，并且同时有社区不断反馈，可以在一些角度证明是相对公允的。

但这也给受众带来了很大的理解难度。像 Terminal-Bench、SWE 很火，大家都去在这个上面评测，受众会觉得它用的人多公允。但对于里面有什么题目、有什么东西，大家没有特别多的认知。

很多人对于专业 bench，最后只看个分数或者少数参数（比如分数+时间，可能这样就会忽略 token efficiency），那本身一个从多角度理解可以保障他公允的东西，经过了一次这种断章取义之后就失真了，一个相对公允的 benchmark 如果受众无法充分理解，那他的价值也会缩减很多。

第二部分就是社媒上各种效果展示，你也搞不清楚是不是 one-shot。很多时候较真一点的受众都会质疑，比如很多社媒上说是 Opus 5.5 做的视频，自己做一下就会发现，也就那么回事。

同时，社媒上也有针对专业 benchmark 进行包装的二次转播（比如非常带歪人对模型能力理解的斩杀线图），这也加剧了专业 benchmark 的评测能力在普通人心中的失真。

我跟葬AI的朋友们最近在思考怎么样让用户更能直观的感受到模型的能力和倾向性差异，而不只是把一个分数摆在广大人民群众面前让大家揣测，这部分工作还在进行中，下一篇文章可能会跟大家分享一下这个工作的设计。
