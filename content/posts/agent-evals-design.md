### 我们先给 Agent 评测下一个定义。

评测也是测，评测就是一个测试工作

传统的软件工程中的测试工作是服务于迭代后验证系统行为是否符合预期的，这一点上没有区别，那么为什么单独拎了个词出来叫评测，而不是直接叫模型测试/Agent 测试

跟软件测试工作相比，模型以及 Agent 这些东西迭代的时候，改动的不确定非常强，以本文主要讨论的 Agent 举例，具体有两方面的不确定性：

1. Agent 依赖模型的输出，人类对模型的输出的控制能力是有限的，可以说是低于对一个传统软件代码系统的控制能力的。
2. Agent 是一个内部耦合性很强的系统，并且他的内部复杂程度跟模型的随机性之间还是在做一个乘法，你在改一个东西的时候，比如你改了第一句 Prompt，可能就会对最后一句 Prompt 所要求的有影响。这个 Prompt 写的比较多的人应该都有感受，你在 Comfy 里面用生图的时候，想搞出一个效果，很多时候要求你对每一个关键词都有很精细的了解。

Agent 在迭代中，想要的效果和实现方式之间，它有一定程度关联，相比于训练模型也有一定程度的可控性，但整体来说对人类还是比较黑盒的。

把它的逻辑完全梳理清楚，是一件太困难的事情，对人的要求非常高。所以评测从正常软件开发里的测试里分化出来了，并且相比于传统软件测试，这个工作的重要性也被提了上来。

那么，我们说的 Agent 评测和模型评测有什么区别？

### Agent 评测和模型评测的区别

在 Agent 或者模型工作内部，评测工作往往跟迭代深度绑定，两者放在一起，改进手段和评测目标往往是同源的，会形成同时做裁判和选手的局面。

而对于模型公司来说，在很多能力的迭代上采用跟评测集设计灵感同源的训练集并不算一个致命问题，现有训练范式正是在确保在某些能力方向上考虑到这个问题在内也能做出效果，放到用户手里也能 Work。

相比之下，大部分 Agent Harness 迭代是工程手段工作，并没有哪种工程范式可以做这样的保证。

有句古话叫压缩即智能，为了刷榜/满足评测维度定义服务的训练也存在数据的压缩，多少也有智能，但是 Harness 工作是 Decompression 或者 Steer，Decompression 还谈得上对智能的释放，但很多评测是通过 Steer 完全可以满足的，Steer 在一些程度上就相当于作弊了。

举个例子，我定了一个评测指标是要求 Agent 搜索的时候要尽可能全面，工程老师在 System Prompt ⾥写 ⼀句"没搜到⼆⼗个结果就重试直到搜够"，分数可能⽴刻上升很多，但是实际使用的时候未必是个好的体验。

那么到实际的团队协作方式去看，Agent 的评测和迭代工作就没法像模型团队那样分工，很多模型训练任务可以从评测出发，评测在整个流程里被视为灵感的起源，Agent 完全无法复刻这条路径。

总结一下上述观点：模型评测只定义问题，Agent 评测同时要定义解决⽅案，难度更高，难以跟现有的模型迭代一样分工。

评测的设计有两部分

1. 第一部分是比较产品角度的，非技术人士和用户关心的非常多的：怎么样设计题目以及打分机制
2. 第二部分是工程角度的事情：围绕评测的 Infra 应该怎么设计。

工程角度的部分，Anthropic 的文章以及互联网上的各种文章都有很充分的实践经验介绍。

### 围绕 Agent System 迭代的评测设计

Anthropic 对于评测基建的定义中有以下两个部分

- 题目（Task）：A **task** (a.k.a **problem** or **test case**) is a single test with defined inputs and success criteria.
- 评分器（Garder）：A **grader** is logic that scores some aspect of the agent’s performance. A task can have multiple graders, each containing multiple assertions (sometimes called **checks**)**.**

题目和评测是一个 Bench 设计的时候最核心的部分，我们一般提到设计一个评测的时候，指的就是设计这两个东西。

它一般的组织形式就是：有若干个题目（Task）；每个题目里面有若干个评测维度（Anthropic 把这些这个叫做评分器 Grader）。

这些评分器有公用的，比如同样是设计 PPT 和设计网页，可能都会用到视觉相关的评分器去给出意见。

也有专用的，比如设计一道题，题目是计算 6 个宝可梦在进化前和进化后尾巴数量会有多少区别，那么会给这套题写一个专用脚本判断 Agent 最后回答的那个数字是否正确。（本题出自 Gaia Benchmark）

题目和评分的设计是个产品问题。

题目和评分的设计就是产品设计，你的产品需要表现成什么样子，题目和评分就要设计成什么样子。

比如说，你希望你的 PPT  Agent 在设计 PPT 的时候，视觉上能表现出一个特征：PPT 的色彩系统设计就是 PPT 所介绍的主体的设计，比如一个 PPT 是介绍一个麦当劳汉堡的，麦当劳的主题色是黄色和红色，那这个PPT也最好设计成黄色和红色。

对于怎么设计评分维度和题目，这里我想分享四条主要经验：

#### 先确定评分指标再确定题目

我观察到很多人在做评测集的时候，习惯性做的事情是一上来就直接开始想题目。然后就陷入一种非常抓瞎的状态，这个时候往往会纠结这个题目是不是不太合适？这题目能不能体现出我要表现出的产品能力？以及各种类似的纠结。

这个事情的原因是，设计Agent产品的时候，我们知道，我们要处理的用户任务是不可枚举的，它里面可能有些高频、有些低频，不同的任务之间也会有组合，组合的时候会有先后顺序，并且用户完全是自然语言输入。

总之，我们不可能把用户所有处理任务都枚举出来，用这些任务去代表我们的产品就提供这些能力，这是不可能的。

如果跨过评分指标的设计直接去尝试设计题目，这题目其实跟你的产品设计目标之间总会存在一些 GAP，所以从我们的产品想呈现出什么样的东西，也就是我们对好坏的判断这个角度出发，先设计好打分机制，再去设计题目。

然后可能每个题目再设计一些更具体的、针对这道题的打分。这可能是一个我自己用下来更好的流程。

我们可以捞一堆用户的反馈起来看，这些里面有哪些共性，比如对于设计类的任务，用户往往都反馈希望设计出来的东西符合某些标准，那就根据这个标准写个评测维度，

比如你可以写个评测维度，输入一个做介绍一个物品类的 PPT，然后打分标准之一是，Ppt 的主题色是否和所介绍的物品的主题色差不多。

我们也可以从你生活中见到的各种理论里面提取，比如Manus 就从语言学中理解出的「隐喻率」（超链接：https://mp.weixin.qq.com/s/2CXssAsQMxdPn_5aLcaijw），然后可以直接根据这个客观道理去定评测维度，比如一篇调研报告里使用隐喻的地方共有多少处统计一下。

或者直接定义好要的产品特性，比如我要设计一个做设计Agent，那我对我的产品的定义一定是：

我要设计比较好看的动效；

如果是一个有流程的东西，我的动效在这里面要做到特别强，还是做到不喧宾夺主；

然后再根据这些去确定好的去设计或者把用户的反馈固化成题目，确定了这些指标之后，设计具体的题目会变得容易很多。

#### 可观测性是评测工作里最重要的部分

围绕大语言模型的工作很多时候非常像是一门实践学科，可观测性是实践学科中最重要的实验设计原则之一。 尤其对于那些依赖反复试验、反馈和迭代来积累知识的学科，可观测性几乎是实验能够产生有效知识的前提。

我们设想一个最极端的评测设计，先不确认任何指标，我只把结果拿出来铺出来，比如最后产出的结果、结果的截图、录屏视频；我的所有设计目标都服务于把产出的结果尽可能方便地展示给受众，可能包括：

1. 它做了一个前端，有截图预览和完整的交互预览。
2. 它做了一个视频，有一个录屏预览。
3. 它的路径，他每一步行动 Summary。
4. 它用了多少时间，它用了多少 Token，用的什么 Effort，加载了哪些 Skill。
5. 它基于哪个 Harness。
6. 以及还有其他能想到的各种要素。

那么，其实观测者不需要我给他指导，他依靠自己的主观喜好直接去看也可以给出一个对于哪个结果好那个结果坏的判断。然后观测者再把自己的主观喜好梳理清楚，那就能设计出来一个更可靠的评分维度。

#### 接受定义评测维度时的主观性并且为之负责

前面说了要先确定评测维度，但 Agent 作为一个刚刚诞生的技术产品，大家都还搞不清楚该提供何种服务，都还在围着用户问你们都用 Agent 做什么，那么从用户需求角度来看评测维度就是非常难确定的。

任何道理、任何规律刚刚诞生后都是「主观定义」，「客观标准」是经历了长久的时间时候形成的「主观定义」。

但 Agent 这个技术和产品都刚诞生没多久，很多定义没有被大量的使用检验过，难以形成共识。

另外，Agent 评测还需要评测轨迹，评测针对任务的某个中间步骤中 Agent 的运作方式等等大量并不直接跟用户需求相关的东西，这些更难以寻找确切的标准。所以我们要接受自己去做一些主观的判断，并且为之负责。

在摸索的过程中，评测可以作为描述自己对产品和整体架构认知的核心手段，作为 Harness 核心维护者，脑子里要尽可能了解自己的系统是怎么运行的，在什么样的条件下会有什么样的行为，评测就是这些行为的具象化。

#### 动态性比较强的 Task

举个例子，比如说我让他去帮我检索每天国际政治新闻出了哪些大事儿，这样，然后他每天搜出来的东西可能都不一样。

但是，我的一个Valuation可能跑在两个不同的天，就是我没法儿把搜索的这个环境固定下来。

这个 Task 的评测有两个问题，一个是没办法常规意义上进行完成与否的校验，另一个是不稳定，每一天的搜索结果可能不一样。

有两种手段可以进行这种问题的评测，第一种是为了实验稳定性以及公平，可以考虑构建一个 Internet Archive + Search 的基建来进行评测，在迭代细节的时候使用。第二种我认为可以在设计题目的时候将环境的动态性考虑进来，然后以暴露问题为目的定义评测维度，这种是可以考虑用来每天日常运行，方便观测和暴露问题的，寻找迭代灵感的。

比如，我可以设计一个这样的评测题目：

我们的题目设计为让 Agent 去搜集 50 个国际大事新闻。然后校验标准设计为，我们通过脚本或者 Api 的形式去抓 100 个新闻网站的当天的新闻列表，比如路透社和Bbc。

然后再结合这两份数据进行评测维度定义，比如：

1. 我去判断一下这 50 个国际大事，在多少个新闻网站里出现过。代表它抓的准确性或者权威性什么之类的。
2. 有多少个没有在新闻网站里出现过。代表它挖小道消息的能力。

现在大部分用户的 Task 实际都有比较强的动态性（甚至绝大部分都依赖搜索，但根据用户要求的产出形式不同以及调研领域的新闻时效性差异，对用户实际的使用感受影响也都不同）。

对于强动态性的任务，要有快照这种服务于对定义好的 Capability 进行 Regression 的方案，同时也要建立基于真实世界的评测维度来服务于发现迭代灵感的。

## 用户和传播角度的评测

除了专业的评测设计，还有一个话题我认为尤为重要，就是用户视角的评测，这里有两个问题，一个是用户怎么样理解一个模型或者一个 Harness 的能力以及表现出某种倾向性的原因，另一个是用户怎么看待现有的各种评测分数。

#### 现有广泛传播的评测的问题

现在大部分人，不只是用户，甚至包括专业从业者，也没有时间专门测试一个模型的表现。人们能看到的模型效果展示非常鱼龙混杂。

现在能接触到的 Bench 分两部分。

第一部分是专业的 Benchmark，每个模型发布的时候都会跑，有配套论文，他们在设立的时候定了很多指标，再通过一些论证去证明它合理，并且同时有社区不断反馈，可以在一些角度证明是相对公允的。

但这也给受众带来了很大的理解难度。像 Terminal-Bench、SWE 很火，大家都去在这个上面评测，受众会觉得它用的人多公允。但对于里面有什么题目、有什么东西，大家没有特别多的认知。

很多人对于专业 Bench，最后只看个分数或者少数参数（比如分数+时间，可能这样就会忽略 Token Efficiency），那本身一个从多角度理解可以保障他公允的东西，经过了一次这种断章取义之后就失真了，一个相对公允的 Benchmark 如果受众无法充分理解，那他的价值也会缩减很多。

第二部分就是社媒上各种效果展示，你也搞不清楚是不是 One-Shot。很多时候较真一点的受众都会质疑，比如很多社媒上说是 Opus 5.5 做的视频，自己做一下就会发现，也就那么回事。

同时，社媒上也有针对专业 Benchmark 进行包装的二次转播（比如非常带歪人对模型能力理解的斩杀线图），这也加剧了专业 Benchmark 的评测能力在普通人心中的失真。

我跟葬Ai的朋友们最近在思考怎么样让用户更能直观的感受到模型的能力和倾向性差异，而不只是把一个分数摆在广大人民群众面前让大家揣测，这部分工作还在进行中，下一篇文章可能会跟大家分享一下这个工作的设计。

## Agent System 评测和 Harness 迭代

我们前面把评测当成一个独立的概念讲了很多，现在社媒上不断冒出来各种独立的概念：Prompt Engineer、Context Engineer、Harness Engineering 等等各种新奇的功底。

我觉得他们每一个词确实有独立代表一些思想，但它们之间的交叉也非常多。

创造概念就是在创造抽象层级，好的抽象可以降低协作成本，所以造词儿这个事儿也不是个坏事，这是提升生产力必须要有的流程，不然程序员们估计还在写汇编语言。

但坏的地方在于，市场太热的时候从业者们会急着造词争夺话语权，大家创造出来的大部分概念完全不具备一层好的抽象应该符合的基本要素，像 Skill，Agent，Harness 这些东西到底是个啥也说不清楚，较真的用户和从业者们遇上了也一头雾水，本来是一个应该造福大家的事情，最后实际产生的作用也只有 Fomo 老板，然后老板们折腾下面的人。

评测也好，Harness Engineering 等词也好，所有围绕模型的工作，还是记住最终的核心目的——让 Ai 表现出符合自己设计目标的效果。

#### 直接抄一个Harness不行吗？

最狭义的 Harness 直就是让 Agent Loop 能正确的跑起来和终止，再加上一些加载 Skill，扩展 Tool 等能力，这个部分里面的实现工作量并不大，搭一个并没有多大难度，或者直接基于 Pi 或者 Claude 或者 Openai 的 Agent Sdk 封装甚至把一个已经跑的还不错的 Agent 拷贝下来去魔改，这都不是很困难的事情。

但实际业务跑起来的时候，你会收到用户各种各样的反馈，每个人都会对 Agent 有各种效果上的要求。抄了之后，你得懂里面有什么，还得懂怎么改，又得有评测。不可能抄过来就完全不变了。

所以抄一个 Agent 框架内核解决不了这个问题。

Evals 和 Harness 设计在上一代的工作中的策略产品设计工作最类似，出题出指标就是把脑子里对于什么是好的给呈现出来，

这个东西的最好尝试和做产品是一样的，就是先跑起来在说，很多效果优化项拍脑袋拍不出来，跑一遍看看效果才能想得出来哪儿好哪儿不好，才能发现出题，定指标和设计打分机制的灵感来源。

目前看到的唯一解就是有一个人了解模型+了解模型落地+了解产品+非常又责任心的超级大哥抱着享受探索未知领域的 Mindset 去全盘负责这个事情。

搭个 Agent 没多少代码量和 Prompt 量，但是这个工程里面堪称每一个字符彼此之间都存在耦合，对工程师负责程度和全局最优解的思考程度要求摧毁了并不追求极致的团队的分工体系。

可想而知目前没有几个团队做得好这个事情。这不是人力/钱角度的难，这是一个伟大的为人类进步探索未知的任务！

## Harness 会不会被模型能力吃掉

模型能力不够强的时候，要不要靠工程问题先来兜一部分？对于比较前沿的 Agent 开发者来说，这是一个讨论的很久的问题。

这个问题我个人有以下几个观点：

1. 技术上大家的理解不会差太多，但是产品角度，一方面是产品总是要解决最后一公里问题，提供确定性的价值；

另一方面很多商业决策都有个时不我待的问题，如果依赖模型的迭代来让让 Agent 变得更好，不论是等待前沿模型更新还是自己根据需求做后训练，迭代周期都太长，工程（Harness）改动的最快几个小时就能完成一轮从定义好问题到改动完成到上限验证。

模型真发展好了，删了也不心疼，甚至你还可以把这个东西卖给模型帮模型发展。

1. 大量 Harness 本身就是由模型训练塑造的，现在的 Harness Engineering 工作就是 Trajectory RL 这条训练路径的产物。
