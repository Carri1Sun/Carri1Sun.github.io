我从 2026 年早些时候我开始接触评测工作，过去半年给 Tabbit Browser，Offloop等及一些朋友的创业项目做过评测或者进行过交流，这些项目大部分类似一个 通用Agent 的形态。

这篇文章是 2026 年 10 月开始写的，主要分享我做 General Agent System 评测工作时的一些经验，Agent 评测是验证围绕一个 Agent 的改动手段是否能达到预期同时维持系统稳定的一套系统，这套系统要考虑到 Agent 这个技术内部的耦合性以及迭代中的不可控性等前提，确定一些题目和评分标准，然后在迭代中持续进行观测。

后文把 General Agent System 简写成 Agent，这篇文章的经验同样适用于 Harness、Prompt 和 Skill 等的迭代（这些都是一个 Agent 的子模块）。

## 一、Agent 评测的定义

评测也是测，评测就是一个测试工作。

传统的软件工程中的测试工作是服务于迭代后验证系统行为是否符合预期的，这一点上没有区别。

那为什么单独拎了个词出来叫评测，而不是直接叫模型测试/Agent测试？

跟软件测试工作相比，模型及 Agent 迭代的时候，改动的不确定非常强，以本文主要讨论的 Agent 举例，具体有两方面的不确定性：

1. Agent 依赖模型的输出，模型的输出是有不可预期性的，人类操控 Agent 的工具“语言”本身也是存在大量歧义的，人类对模型的输出的控制能力是有限的，可以说是远低于对一个传统软件代码系统的控制。
2. Agent 是一个内部耦合性很强的系统，并且它的内部复杂程度跟模型的随机性之间是在做一个乘法，你改了第一句 Prompt，可能会令另一句 Prompt 所要求的行为也产生影响。
   1. 比如：我的 Agent 本来有一个计划机制，Prompt 写的是“在开始任务之前进行计划”，后面迭代中我想要加一个对简单问答直接回答的机制，如果通过改 Prompt 的方式来迭代，新加这一句 Prompt 的时候就必须考虑到跟对于计划的要求不打架（同时这里也需要评测来明确具体什么样的 case 出计划是合理的）

这个 Prompt 写的比较多的人应该都有感受，你在 Comfy UI里面用生图的时候，想搞出一个效果，很多时候要求你对每一个关键词及他们之间的关联有很精细的了解，加一个不合适的风格的描述词可能把原本定好的角色发色和光影效果等全部带偏。

Agent 在迭代中，想要的效果和实现方式之间有一定程度关联，相比模型训练也有一定程度的可控性，但整体来说对人类还是比较黑盒的。

把它的逻辑完全梳理清楚是一件太困难的事情，对人的要求非常高。

所以评测就从正常软件开发里的测试分化了出来，并且相比于传统软件测试，工作的重要性也被提了上来。

不过，Agent 评测和模型评测到底有什么区别？

## 二、Agent 评测和模型评测的区别

在 Agent 或者模型工作内部，评测工作往往跟迭代深度绑定，两者放在一起，改进手段和评测目标往往是同源的，会形成同时做裁判和选手的局面。

而对于模型公司来说，很多能力的迭代上采用跟评测集设计灵感同源的训练集并不算一个致命问题。因为现有训练范式正是在确保在某些能力方向上考虑到这个问题在内也能做出效果，放到用户手里也能Work。

相比之下，大部分 Agent Harness 迭代是工程手段工作，并没有哪种工程范式可以做这样的保证。

有句古话叫压缩即智能，为了刷榜/满足评测维度定义服务的训练虽然是数据的压缩，但多少也有智能。

可Harness 工作是 Decompression（解压缩） 或者 Steer（引导），Decompression 还谈得上对智能的释放，但很多评测是通过 Steer 完全可以满足的，Steer 在一些程度上就相当于作弊了。

举个例子，我定一个评测指标是要求 Agent 搜索的时候要尽可能全面，工程老师在Prompt ⾥写⼀句「没搜到⼆⼗个结果就重试直到搜够」，分数⽴刻上升很多，但实际使用未必是个好的体验。

再到实际的团队协作方式去看，Agent 评测和迭代就没法像模型团队那样分工。很多模型训练任务可以从评测出发，评测在整个流程里是灵感的起源，但Agent 完全无法复刻这条路径。

总结一下上述观点：模型评测只定义问题，Agent 评测同时要定义解决⽅案，难度更高，难以跟现有模型迭代一样分工。

## 三、Agent 评测入门

实践上，这个工作有很多工程范式，现有资料里面我觉得看这个比较好

https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents

评测的设计有两部分

1. 第一部分是比较产品角度的，非技术人士和用户关心的非常多的：怎么样设计题目以及打分机制
2. 第二部分是工程角度的事情：围绕评测的 Infra 应该怎么设计。

工程角度的部分，Anthropic 的文章以及互联网上的各种文章都有很充分的实践经验介绍。

我们接下来分享下做第一部分工作时遇到的难点以及积累的解决经验，这里主要有两部分，第一部分分享下我是怎么理解公开的 Bench 的设计和迭代，另一部分是围绕内部产品迭代设计 Bench 时的一些经验。

### 围绕 Agent System 迭代的评测设计

Anthropic 对于评测基建的定义中有以下两个部分

- 题目（Task）：A task is a single test with defined inputs and success criteria.（一项包含明确定义的输入和成功标准的单一测试）
- 评分器（Garder）：A grader is logic that scores some aspect of the agent’s performance. A task can have multiple graders, each containing multiple assertions .

题目和评测是一个 Bench 设计时候最核心的部分，它一般的组织形式就是：有若干个题目（Task）；每个题目里面有若干个评测维度。

这些评分器也有公用的，比如同样是设计 PPT 和设计网页，可能都会用到视觉相关的评分器去给出意见；

也有专用的，比如设计一道题，题目是计算 6 个宝可梦在进化前和进化后尾巴数量会有多少区别，那么会给这套题写一个专用脚本来判断 Agent 最后回答的那个数字是否正确。（本题出自 Gaia Benchmark）

其中，题目和评分的设计是一个产品问题。你的产品要表现成什么样子，题目和评分就要设计成什么样子。

对于怎么设计评分维度和题目，这里我想分享四条主要经验：

#### 1）先确定产品的评分指标再确定题目

我观察到很多人在做评测集的时候，习惯性做的事情是一上来就直接开始想题目。然后就陷入一种非常抓瞎的状态，陷入这个题目是不是不太合适、这个题目能不能体现出我要表现出的产品能力之类的纠结情况。

这个事情的原因是，设计Agent产品的时候，我们就知道要处理的用户任务是不可枚举的。

它里面可能有些高频、有些低频，不同的任务之间也会有组合，组合的时候会有先后顺序，并且用户完全是自然语言输入。

所以，我们是不可能把用户所有处理任务都枚举出来，用这些任务去代表我们的产品。

如果跨过评分指标设计去设计题目，这题目其实跟你的产品设计目标之间总会存在一些 GAP。

所以应该从我们的产品想呈现出什么样的东西，也就是我们对好坏判断的角度出发，先设计好打分机制，再去设计题目。

然后可能每个题目再设计一些更具体的、针对这道题的打分。这可能是一个我自己用下来更好的流程。

我们可以捞一堆用户的反馈起来看，这些里面有哪些共性，比如对于设计类的任务，用户往往都反馈希望设计出来的东西符合某些标准，那就根据这个标准写个评测维度。

比如你可以写个评测维度，输入一个做介绍一个物品类的 PPT，然后打分标准之一是，PPT的主题色是否和所介绍的物品的主题色差不多。

我们也可以从你生活中见到的各种理论里面提取，比如Manus 就从语言学中理解出的「隐喻率」（超链接：https://mp.weixin.qq.com/s/2CXssAsQMxdPn_5aLcaijw）。

或者直接定义好要的产品特性，比如我要设计一个做设计Agent，那我对产品的定义一定是：

要设计比较好看的动效；

有相应的流程；

动效在里面要做到特别强，还是不喧宾夺主。

随后，再根据这些确定设计，或者把用户反馈固化成题目。

#### 2）可观测性是评测工作里最重要的部分

围绕大语言模型的工作很多时候像一门实践学科，而可观测性是实践学科中最重要的实验设计原则之一。 

尤其对于那些依赖反复试验、反馈和迭代来积累知识的学科，可观测性几乎是实验能够产生有效知识的前提。

我们设想一个最极端的评测设计，先不确认任何指标，只把结果拿出来铺出来，比如最后产出的结果、结果的截图、录屏视频。

我的所有设计目标都服务于把产出的结果尽可能方便地展示给受众，可能包括：

1. 它做了一个前端，有截图预览和完整的交互预览
2. 它做了一个视频，有一个录屏预览
3. 它的路径，他每一步行动 Summary（摘要）
4. 它用了多少时间，它用了多少 Token，用的什么 Effort（推理强度），加载了哪些 Skill
5. 它基于哪个 Harness
6. 以及还有其他能想到的各种要素

那观测者不需要我给他指导，依靠自己的主观喜好直接去看，也可以给出对结果好坏的判断。所以观测者把自己的主观喜好梳理清楚，就能设计出一个更可靠的评分维度。

#### 3）做主观判断的实验并且负责

有两类问题，我们在建立评价维度时非常困难的

1. 如果我们去看用户的反馈和社媒上的用法分享，会观察到这个信息：大量用户的用法中，对于 agent 给的结果的好与不好的评价是非常主观的，就是像一篇文章好不好看，一个东西的视觉稿子好不好，或者说一个游戏好不好玩这种东西。这类问题的评测对于模型和 Agent 迭代都是难题。
2. Agent 作为一个刚诞生的技术产品，大家都还搞不清楚该提供何种服务，都还围着用户问你们怎么用 Agent 以及都用 Agent 做什么，另外，Agent 评测还需要评测轨迹，评测针对任务的某个中间步骤中 Agent 的运作方式等等，大量不直接跟用户需求相关的东西，更难以寻找确切的标准。

我们前一节提到了我们的工作很像一门实践学科，实践学科的重要工作 mindset 之一是：敢下主观判断，不用特别纠结于推理演绎，直接下判断然后再去做实验观测。

任何道理、任何规律刚刚诞生后都是「主观定义」，「客观标准」是经历了长久的时间时候形成的「主观定义」。

Agent 这个技术和产品形态都刚诞生没多久，很多定义没有被大量的使用检验过，难以形成共识，在推演一个设计是否合理的时候也难以寻找完全可信的论据。

所以我们要接受自己去做一些主观的判断，并为之负责，一个开发者认为自己的 Agent 就应该表现出某种产品特性，但是他无法通过已有证据证明这个特性到用户手里是否是真的好，那他没有必要继续寻找证据，完全可以直接找用户来做 pairwise（对比打分）或者发上线直接做 AB Test 看用户好评率。

同时，在摸索的过程中，评测可以作为描述自己对产品和整体架构认知的核心手段。

作为 Harness 的核心维护者，脑子里要尽可能了解自己的系统是怎么运行的，在什么样的条件下会有什么样的行为——评测就是这些行为的具象化。

#### 4）跟真实世界关联性比较强的 Task

对于跟真实世界关联性很强的任务，要有两套评测机制：

1. 给有时效性的信息搞一套快照，来对一个很明确的我们要实现的 Capability（能力）进行 Regression（回归测试） 。
2. 直接基于真实世界的运行任务，从里面提取迭代灵感以及建立评测维度。

举个例子，我让Agent帮我检索每天国际政治新闻，他每天搜出来的东西是不一样的，所以我无法把搜索的环境固定下来。

这类Task 评测有两个问题，一个是无法常规意义上进行完成与否的校验；另一个是不稳定，每天的搜索结果可能都不一样。

有两种手段可以进行这类问题的评测，第一种是构建一个 Internet Archive + Search（ 网络存档 + 搜索）的基建来进行基本的搜索能力的评测；

第二种是在设计题目的时候将环境的动态性考虑进来，然后以暴露问题为目的来每天运行，方便寻找评测维度。

举个例子，我们让 Agent 去搜集 50 个国际大事新闻，再通过脚本或者 API 的形式去抓 100 个新闻网站当天的新闻列表。

再结合这两份数据进行评测维度定义：

1. 判断一下这 50 个国际大事，有多少在多少个新闻网站里出现过，可以展现它抓的准确性或者权威性。
2. 有多少个没有在新闻网站里出现过，代表它挖小道消息的能力；

这类评测是可以考虑用来每天日常运行，方便观测、暴露问题和寻找迭代灵感的。事实上，现在实际上存在大量用户实际发起的任务，都依赖真实世界中有时效性的信息。

## 四、关于Agent System 评测和 Harness 迭代

### 4.1 Harness 会不会被模型能力吃掉

模型能力不够强的时候，要不要靠工程问题先来兜一部分？这是一个被很多Agent 开发者讨论很久的问题。

我个人观点是：

1. 技术上大家的理解不会差太多，但一方面是产品总是要解决最后一公里问题，提供确定性的价值；

另一方面很多商业决策都有个时不我待的问题，如果依赖模型的迭代来让让 Agent 变得更好，不论是等待前沿模型更新还是自己根据需求做后训练，迭代周期都太长。

工程（Harness）改动的最快几个小时，就能完成一轮从定义好问题到改动完成到上限验证全流程。模型真发展好了，删了也不心疼，甚至还可以把这个东西卖给模型。

1. Harness 工作的一大部分内容是理解模型能力并且把它激发出来。

“智力”这个抽象的词其实误导了很多人对模型的理解，模型的很多行为都是针对性的进行训练而表现出的，并非完全不可预期的，并不需要用“智力”“审美”这种抽象的词汇来理解模型。

比如 claude 的模型训练了大量的设计风格数据，gpt 的模型训练了大量如何验证一个任务是否完成的数据，开发者的 harness engineer 工作就应该是看如何 prompting 好让模型也表现出这些行为。

即使模型进步了，Harness 也绝对不可能变成冲着模型吼一句“不完成就不要停下来”或者“把这个页面做的好看”然后模型就能稳定的满足一个模糊的预期。

1. 很多 Harness 工作是跟模型训练共同进步共同演化的，现在的 Harness Engineering 工作中的很多特征，比如看轨迹，纠错，验证，交付等等流程，都是在对齐或者延伸 Agentic RL 阶段的训练数据分布，同时也是这种 Harness 的工作良好促进了模型继续使用这种 Harness 下积累的数据进行训练。

### 4.2那直接抄一个Harness可行吗？

最狭义的 Harness 就是让 Agent Loop 能正确跑起来和终止，再加上一些加载 Skill，扩展 Tool 等能力，这个部分里面的实现工作量并不大，搭一个并没有多大难度。

直接基于 Pi 或者 Claude 或者 Openai 的 Agent SDK 封装，甚至把一个已经跑的还不错的 Agent 拷贝下来去魔改，都不是很困难的事情。

但实际业务跑起来的时候，你会收到用户各种各样的反馈，每个人都会对 Agent 有各种效果上的要求。抄了之后，你得懂里面有什么，还得懂怎么改，又得有评测。不可能抄过来就完全不变了。

所以抄一个 Agent 框架内核解决不了问题。

Evals 和 Harness 设计在上一代工作中和策略产品设计工作最类似，出题出指标就是把脑子里对于什么是好的给呈现出来。

所以这个工作和做产品是一样的，就是先跑起来在说。很多效果优化项拍脑袋拍不出来，跑一遍看看效果才能想得出来哪儿好哪儿不好。

目前看到的唯一解就是有个了解模型+了解模型落地+了解产品+非常有责任心的超级大哥，抱着享受探索未知领域的 Mindset 去全盘负责这个事情。

搭个 Agent 没多少代码量和 Prompt 量，但这个工程里面堪称每一个字符彼此之间都存在耦合，对工程师负责程度和全局最优解思考程度的要求摧毁了并不追求极致的团队分工体系。（沐秋：这句话建议多读两遍）

可想而知目前没有几个团队做得好这个事情。这不是人力/钱角度的难，而是一个为人类进步探索未知的伟大任务！

## 五、最后一些碎碎念：

### 5.1模型大造词

我们前面把评测当成一个独立概念讲了很多，现在社媒上不断冒出来各种独立概念：Prompt Engineer、Context Engineer、Harness Engineering 等各种新奇的词语...

我觉得这些词确实在独立代表一些思想，但它们之间的交叉也极多。

创造概念就是在创造抽象层级，好的抽象可以降低协作成本，所以造词也不是个坏事，是提升生产力必须要有的流程，不然程序员们估计还在写汇编语言。

但坏的地方在于，市场太热的时候从业者们会急着造词争夺话语权，大家创造出来的大部分概念完全不具备一层好的抽象应该符合的基本要素。

像 Skill、Agent、Harness 这些东西到底是个啥也说不清楚，较真的用户和从业者们遇上了也一头雾水，本来是一个造福大家的事情，但最后实际产生的作用只有 FOMO 老板，然后老板们折腾下面的人。

评测也好，Harness Engineering 等词也好，所有围绕模型的工作，还是要记住核心目的——让AI表现出符合自己设计目标的效果。

### 5.2 用户视角的评测

除了专业的评测设计，还有一个话题我认为尤为重要，就是用户视角的评测。

这里有两个问题，一个是用户怎样理解一个模型，或者理解Harness的能力及表现出某种倾向性的原因，另一个是用户怎么看待各种评测分数。

现有广泛传播的评测是有明显问题的。大部分人，不只是用户，甚至包括专业从业者，也没有时间专门测试一个模型的表现，所以人们能看到的模型效果展示非常鱼龙混杂。

日常大伙现在能接触到的 Bench主要分两部分。

第一部分是专业的 Benchmark。每个模型发布的时候都会跑、有配套论文，他们在设立的时候定了很多指标，再通过论证去证明它合理，并且同时有社区不断反馈，在一些角度证明是相对公允的。

但也给受众带来了很大的理解难度。像 Terminal-Bench、SWE 很火，大家都在这个上面评测，受众会觉得它用的人多公允。但对里面有什么题目、有什么东西，大家没有特别多的认知。

很多人对专业 Bench，最后只看个分数或者少数参数（比如分数+时间，但这样就会忽略 Token Efficiency），那本身一个从多角度理解可以保障他公允的东西，经过了一次断章取义后就失真了。

一个相对公允的 Benchmark 如果受众无法充分理解，那它的价值也会缩减很多，甚至存在误导。

第二部分就是社媒上各种效果展示，你也搞不清楚是不是 One-Shot。很多较真一点的受众都会质疑，比如很多社媒上 Opus 5.5 做的视频，自己做一下就会发现也就那么回事。

我最近也在思考怎么样让用户更能直观感受到模型的能力和倾向性差异，而不是把一个分数摆在广大人民群众面前让大家揣测。这部分工作还在进行中，下一篇文章可能会跟大家分享一下这个工作的设计。
