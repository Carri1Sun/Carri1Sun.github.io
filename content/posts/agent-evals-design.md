### 我们先给 Agent 评测下一个定义。

评测也是测，评测就是一个测试工作

跟软件测试工作相比，模型以及 Agent 这些东西迭代的时候，改动的不确定非常强，有些东西不是说你做了逻辑 A，就一定能产出逻辑 B，具体有两方面的不确定性：

1. 它依赖模型的随机输出。
2. Agent 是一个内部耦合性很强的系统，并且他的内部复杂程度跟模型的随机性之间还是在做一个乘法，你在改一个东西的时候，比如你改了第一句 prompt，可能就会对最后一句 prompt 所要求的有影响。这个 Prompt 写的比较多的人应该都有感受，你在 comfy 里面用生图的时候，想搞出一个效果，很多时候要求你对每一个关键词都有很精细的了解。

这对人来说是比较黑盒的。虽然它有一定程度的对应关系，相比于训练模型也有一定程度的可控性（现在看可能跟现在的专项数据优化的路径差不多了），但让人把它的逻辑完全梳理清楚，是一件太困难的事情，对人的要求非常高。所以评测从正常软件开发里的测试里分化出来了，并且相比于后者，他的重要性也被提了上来。

由此引伸出来的问题是，Agent 评测和模型评测有什么区别

### Agent 评测和模型评测的区别

在 Agent 或者模型工作内部，评测工作往往跟迭代深度绑定，两者放在一起，改进手段和评测目标往往是同源的，会形成同时做裁判和选手的局面。

而对于模型公司来说，在很多能力的迭代上采用跟评测集设计灵感同源的训练集并不是问题，现有训练范式正是在确保这样也能做出效果，放到用户手里也能 work。

相比之下，大部分 Agent Harness 迭代是工程手段工作，并没有哪种工程范式可以做这样的保证。

有句古话叫压缩即智能，为了刷榜/满足 rubric 定义服务的训练也存在数据的压缩，多少也有智能，但是 harness 工作是 decompression 或者 steer，decompression 还谈得上对智能的释放，但很多评测是通过 steer 完全可以满足的，steer 在一些程度上就相当于作弊了。

举个例子，评测要求"搜得全"，我在 harness ⾥写 ⼀句"没搜到⼆⼗个结果就重试直到搜够"，分数⽴刻上去，但是实际使用的时候未必是个好的体验。

那么到实际的团队协作方式去看，Agent 的评测和迭代工作就没法像模型团队那样分工，很多模型训练任务可以从评测出发，评测在整个流程里被视为灵感的起源，Agent 完全无法复刻这条路径。

如果真的团队里独立出来一个比较大的评测团队，它能做的事情主要也就是用于防退化的约束，定位问题在模型还是⼯具还是 context 的归因，把⼈在看 agent 的运行路径和产物时浮现出的判断灵感变成可以重复使用的校准。

给上述观点一个结论：模型评测只定义问题，Agent 评测同时要定义解决⽅案，难度更高

评测的设计有两部分

1. 第一部分是比较产品角度的，非技术人士和用户关心的非常多的：怎么样设计题目以及打分机制
2. 第二部分是工程角度的事情：Infra 应该怎么设计。

我们先讨论下第一部分的经验和难点。

## Agent 评测的难点是什么？

### Case （题目）和 Grader （打分器）是个产品问题

这两个东西在样子上是很好理解的。它一般的组织形式就是：你有若干个题目，也就是若干个 Case；每个 Case 里面有若干个打分器。

这些打分器有公用的，比如同样是设计 PPT 和设计网页，可能都会用到视觉相关的打分器去给出意见；也可能有专用的，比如对于某一道题，要写一个脚本判断最终输出结果是否符合标准。

所以，Case 和 Grader 的设计，就是你认为你的产品需要表现成什么样子，比如说，比如说，你希望你的 PPT Agent 在设计PPT的时候，视觉上能表现出一个特征：假如你的PPT是介绍一个麦当劳汉堡的，麦当劳的主题色是黄色和红色，那这个PPT也最好设计成黄色和红色。

这里我有四条主要经验：

#### 接受主观并且为之负责

评测的核心是定指标，但是 Agent 作为一个刚刚诞生的技术产品，大家都还搞不清楚该提供何种服务，都还在围着用户问你们都用 Agent 做什么，从用户需求角度指标就是非常难确定的。

所谓的客观标准也都是经历了长久的时间时候形成共识的主观定义，但 Agent 这个技术还没有经过漫长时间的洗礼，难以形成，我们要接受自己下一些主观的判断，并且为之负责。

另外，Agent 评测还需要评测轨迹，评测针对任务的某个中间步骤中 agent 的运作方式等等大量并不直接跟用户需求相关的东西，这些更难以寻找确切的标准。

在摸索的过程中，评测可以作为描述自己对产品和整体架构认知的核心手段，作为 harness 核心维护者，脑子里要尽可能了解自己的系统是怎么运行的，在什么样的条件下会有什么样的行为，评测是这些行为的显化。

#### Agent 不是完美的产品呈现形式

至少几个季度内，agent 是个用户们（至少是高阶用户们）要学着去怎么用的更好的一个东西，这个角度看做 Agent 像做个精密的工具，那么从这个角度出发，我们就要针对内部结构的运转去做评测。也就是评 trajectory，这个难点是建立指标不能从传统的需求理解出发，但是好在 best practice 依然适用，跑起来看看就能知道什么样的 trajectory 是好的。

#### 先设计 Garder 再设计题目

我观察到很多人在做评测集的时候，习惯性做的事情是一上来就直接开始想题目。然后就陷入一种非常抓瞎的状态，这个时候往往会纠结这个题目是不是不太合适？这题目能不能体现出我要表现出的产品能力？以及各种类似的纠结。

这个事情的原因是，设计Agent产品的时候，我们知道，我们要处理的用户任务是不可枚举的，它里面可能有些高频、有些低频，不同的任务之间也会有组合，组合的时候会有先后顺序，并且用户完全是自然语言输入。总之，我们不可能把用户所有处理任务都枚举出来，用这些任务去代表我们的产品就提供这些能力，这是不可能的。

那么题目其实跟你的产品设计目标之间总会存在一些 gap，所以从我们的产品想呈现出什么样的东西，也就是我们对好坏的判断这个角度出发，先设计好打分机制，再去设计题目。然后可能每个题目再设计一些更具体的、针对这道题的打分。这可能是一个我自己用下来更好的流程。

比如我要设计一个做设计的Agent，那我对我的产品的定义一定是：我要设计比较好看的动效；如果是一个有流程的东西，我的动效在这里面要做到特别强，还是做到不喧宾夺主；我的用色应该是什么样的。

我想到的应该是这些表现上的东西，而不是具体的题目。有了这些表现之后，设计具体的题目会发现容易很多。

#### Observability （可观测性）是评测工作里最重要的部分

设想一个最极端的情况

我做一个公开的评测，我不确认任何指标，我只把结果拿出来铺出来，比如最后产出的结果、结果的截图、视频或者录屏；如果是一个前端，也可以直接发上去。我把这些东西尽可能全地展示出来给受众，可能包括：

1. 它做了一个前端，有一个截图预览
2. 它做了一个视频，有一个了录屏预览
3. 它的路径，他每一步行动 summary 一个原油
4. 它用了多少时间，它用了多少 token，用的什么 effort，加载了哪些 skill
5. 它基于哪个 harness。
6. 以及还有其他能想到的各种要素

我的目的是，把产出的结果尽可能方便地展示给受众，而不是告诉受众某个角度某个指标一定是好的。

那么，其实受众不需要我给他指导，也完全可以判断哪个好、哪个不好。

## 那么，不断地让agent变得更好有没有价值？Harness会不会被模型能力吃掉

模型能力不够强的时候，要不要靠工程问题先来兜一部分？对于比较前沿的 Agent 开发者来说，这是一个讨论的很久的问题。

这个问题我个人有以下几个观点：

1. 技术上大家的理解不会差太多，但是产品角度，一方面是产品总是要解决最后一公里问题，提供确定性的价值，另一方面很多商业决策都有个时不我待的问题，如果依赖模型的迭代来让让 Agent 变得更好，不论是等待前沿模型更新还是自己根据需求做后训练，迭代周期都太长，工程（harness）改动的最快几个小时就能完成一轮从定义好问题到改动完成到上限验证。模型真发展好了，删了也不心疼，甚至你还可以把这个东西卖给模型帮模型发展。
2. 大量 harness 本身就是由模型训练塑造的，现在的 harness engineering 工作就是 trajectory rl  这条训练路径的产物。

## 那么，直接抄一个Harness不行吗？

最狭义的 Harness 直就是让 Agent Loop 能正确的跑起来和终止，再加上一些加载 skill，扩展 tool 等能力，这个部分里面的实现工作量并不大，搭一个并没有多大难度，或者直接基于 pi 或者 claude 或者 openai 的 agent sdk 封装甚至把一个已经跑的还不错的 agent 拷贝下来去魔改，这都不是很困难的事情。

但实际业务跑起来的时候，你会收到用户各种各样的反馈，每个人都会对 Agent 有各种效果上的要求。抄了之后，你得懂里面有什么，还得懂怎么改，又得有评测。不可能抄过来就完全不变了。

所以抄一个 Agent 框架内核解决不了这个问题。

evals 和 harness 设计在上一代的工作中的策略产品设计工作最类似，出题出指标就是把脑子里对于什么是好的给呈现出来，

这个东西的最好尝试和做产品是一样的，就是先跑起来在说，很多效果优化项拍脑袋拍不出来，跑一遍看看效果才能想得出来哪儿好哪儿不好，才能发现出题，定指标和设计打分机制的灵感来源。

目前看到的唯一解就是有一个人了解模型+了解模型落地+了解产品+非常又责任心的超级大哥抱着享受探索未知领域的 mindset 去全盘负责这个事情。

搭个 agent 没多少代码量和 prompt 量，但是这个工程里面堪称每一个字符彼此之间都存在耦合，对工程师负责程度和全局最优解的思考程度要求摧毁了并不追求极致的团队的分工体系。

可想而知目前没有几个团队做得好这个事情。这不是人力/钱角度的难，这是一个伟大的为人类进步探索未知的任务！

## Harness：跟模型打交道的 Mindset

对我们来说，把评测当成一个独立的概念讲了很多，现在社媒上不断冒出来各种独立的概念：prompt engineer、context engineer、harness engineering 等等各种新奇的功底。

我觉得他们每一个词确实有独立代表一些思想，但它们之间的交叉也非常多。

创造概念就是在创造抽象层级，好的抽象可以降低协作成本，所以造词儿这个事儿也不是个坏事，这是提升生产力必须要有的流程，不然程序员们估计还在写汇编语言。 

但坏的地方在于，市场太热的时候从业者们会急着造词争夺话语权，大家创造出来的大部分概念完全不具备一层好的抽象应该符合的基本要素，像 skill，agent，harness 这些东西到底是个啥也说不清楚，较真的用户和从业者们遇上了也一头雾水，本来是一个应该造福大家的事情，最后实际产生的作用也只有 FOMO老板，然后老板们折腾下面的人。

评测也好，harness engineering 等词也好，所有围绕模型的工作，还是记住最终的核心目的——让 AI 表现出符合自己设计目标的效果。

### 引导普通人一起追求真理

除了专业的评测设计，还有一个 topic 我认为尤为重要，就是用户视角的评测，具体点说就是用户怎么样理解一个模型或者一个 harness 的能力以及表现出某种倾向性的原因。

这是在引导大众接近事物的本质，这是一个我内心一直追求的事情

### 我对现有广泛传播的评测的认知框架

现在大部分人，不只是用户，甚至包括专业从业者，也没有时间专门测试一个模型的表现。人们能看到的模型效果展示非常鱼龙混杂。

现在能接触到的 bench 分两部分。

第一部分是专业的 benchmark，每个模型发布的时候都会跑，有配套论文，他们在设立的时候定了很多指标，再通过一些论证去证明它合理，并且同时有社区不断反馈，可以在一些角度证明是相对公允的。

但这也给受众带来了很大的理解难度。像 Terminal-Bench、SWE 很火，大家都去在这个上面评测，受众会觉得它用的人多公允。但对于里面有什么题目、有什么东西，大家没有特别多的认知。

很多人对于专业 bench，最后只看个分数或者少数参数（比如分数+时间，可能这样就会忽略 token efficiency），那本身一个从多角度理解可以保障他公允的东西，经过了一次这种断章取义之后就失真了，一个相对公允的 benchmark 如果受众无法充分理解，那他的价值也会缩减很多。

第二部分就是社媒上各种效果展示，你也搞不清楚是不是 one-shot。很多时候较真一点的受众都会质疑，比如很多社媒上说是 Opus 5.5 做的视频，自己做一下就会发现，也就那么回事。

同时，社媒上也有针对专业 benchmark 进行包装的二次转播（比如非常带歪人对模型能力理解的斩杀线图），这也加剧了专业 benchmark 的评测能力在普通人心中的失真。
