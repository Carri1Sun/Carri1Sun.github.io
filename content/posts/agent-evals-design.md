## 评测的目的

评测也是测，评测就是一个测试工作。

区别在于，模型以及 Agent 这些东西迭代的时候，改动的不确定非常强，有些东西不是说你做了逻辑 A，就一定能产出逻辑 B，具体有两方面的不确定性：

1. 它依赖模型的随机输出，这个很好理解，评测在模型领域也是一个比较重要的命题。
2. Agent 是一个内部耦合性很强的系统，并且他的内部复杂程度跟模型的随机性之间还是在做一个乘法，你在改一个东西的时候，比如你改了第一句 prompt，可能就会对最后一句 prompt 所要求的有影响。这个 Prompt 写的比较多的人应该都有感受，你在 comfy 里面用生图的时候，想搞出一个效果，很多时候要求你对每一个关键词都有很精细的了解。

这对人来说是比较黑盒的。虽然它有一定程度的对应关系，相比于训练模型也有一定程度的可控性（现在看可能跟现在的专项数据优化的路径差不多了），但让人把它的逻辑完全梳理清楚，是一件太困难的事情，对人的要求非常高。所以评测从正常软件开发里的测试里分化出来了，并且相比于后者，他的重要性也被提了上来。

## Agent 评测的困扰

在 Agent 或者模型工作内部，评测工作往往跟迭代深度绑定，两者放在一起，改进手段和评测目标往往是同源的，会形成同时做裁判和选手的局面。

而对于模型公司来说，在很多能力的迭代上采用跟评测集设计灵感同源的训练集并不是问题，现有训练范式正是在确保这样也能做出效果，放到用户手里也能 work。

相比之下，Agent Harness 的迭代并没有哪种工程范式可以做这样的保证。

大部分 Agent Harness 迭代是工程手段工作，⼯程作弊极其廉价，⽽且零泛化。评测要求"搜得全"，我在 harness ⾥写 ⼀句"没搜到⼆⼗个结果就重试直到搜够"，分数⽴刻上去，能⼒毫⽆变化。模型侧当然也有刷榜，但模型作弊⾄少还有⼀点泛化的运⽓⸺你为某个⽅向补的数据，可能顺带⻓出别的能⼒，因 为它不是从 A 到 B 的直线。⼯程作弊没有这种运⽓，它精确命中评分点，出了评分点什么都不剩。

那么到实际的团队协作方式去看，Agent 的评测和迭代工作就没法像模型团队那样分工，很多模型训练任务可以从评测出发，评测在整个流程里被视为灵感的起源，Agent 完全无法复刻这条路径。

如果真的团队里独立出来一个比较大的评测团队，它能做的事情主要也就是用于防退化的约束，定位问题在模型还是⼯具还是 context 的归因，把⼈在看 agent 的运行路径和产物时浮现出的判断灵感变成可以重复使用的校准。

## Agent 评测的现有范式

实践上，这个工作有很多工程范式，现有资料里面我觉得看这个比较好

https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents

评测的设计有两部分

1. 第一部分是比较产品角度的，非技术人士和用户关心的非常多的：怎么样设计题目以及打分机制
2. 第二部分是工程角度的事情：Infra 应该怎么设计。

### Case 和 Grader 是个产品问题

这两个东西在样子上是很好理解的。它一般的组织形式就是：你有若干个题目，也就是若干个 Case；每个 Case 里面有若干个打分器。

这些打分器有公用的，比如同样是设计 PPT 和设计网页，可能都会用到视觉相关的打分器去给出意见；也可能有专用的，比如对于某一道题，要写一个脚本判断最终输出结果是否符合标准。

所以，Case 和 Grader 的设计，就是你认为你的产品需要表现成什么样子，比如说，比如说，你希望你的 PPT Agent 在设计PPT的时候，视觉上能表现出一个特征：假如你的PPT是介绍一个麦当劳汉堡的，麦当劳的主题色是黄色和红色，那这个PPT也最好设计成黄色和红色。

这里我有两条主要经验：

#### 先有 Garder 的设计再有题目的设计

我观察到很多人在做评测集的时候，习惯性做的事情是一上来就直接开始想题目。然后就陷入一种非常抓瞎的状态，这个时候往往会纠结这个题目是不是不太合适？这题目能不能体现出我要表现出的产品能力？以及各种类似的纠结。

这个事情的原因是，设计Agent产品的时候，我们知道，我们要处理的用户任务是不可枚举的，它里面可能有些高频、有些低频，不同的任务之间也会有组合，组合的时候会有先后顺序，并且用户完全是自然语言输入。总之，我们不可能把用户所有处理任务都枚举出来，用这些任务去代表我们的产品就提供这些能力，这是不可能的。

那么题目其实跟你的产品设计目标之间总会存在一些 gap，所以从我们的产品想呈现出什么样的东西，也就是我们对好坏的判断这个角度出发，先设计好打分机制，再去设计题目。然后可能每个题目再设计一些更具体的、针对这道题的打分。这可能是一个我自己用下来更好的流程。

比如我要设计一个做设计的Agent，那我对我的产品的定义一定是：我要设计比较好看的动效；如果是一个有流程的东西，我的动效在这里面要做到特别强，还是做到不喧宾夺主；我的用色应该是什么样的。

我想到的应该是这些表现上的东西，而不是具体的题目。有了这些表现之后，设计具体的题目会发现容易很多。

#### Capability 和 Regression

评测集一般至少分为两个部分：Capability 和 Regression

Capability 代表的是产品形态，想把产品设计成什么样，Capability 集里面就应该有什么样的 Garder 以及 Case，比如我想做一个网页设计 Agent "这个智能体擅长做什么？"它们应当从较低的通过率起步，瞄准智能体难以应对的任务，为团队留出一座需要攀登的山峰。

在一批 Capability Case 经历了很多的改动都能表现得非常好的时候，就可以让他们

回归评估问的是："这个智能体是否仍能处理它过去能处理的所有任务？"其通过率应当接近100%。它们用于防止退步，因为分数下降意味着某处出了问题、需要改进。当团队在能力评估上不断攀登时，同时运行回归评估也很重要，以确保改动不会在别处引发问题。

在智能体上线并经过优化之后，通过率很高的能力评估可以"毕业"，成为持续运行的回归测试套件，用以捕捉任何漂移。那些曾经衡量"我们究竟能不能做到这件事？"的任务，此后衡量的便是"我们是否仍能可靠地做到这件事？"


### Observability 是 Infra 里最重要的部分

我不先确定指标，或者说，我主要宣传的东西不是指标，而是效果。比如最后产出的结果、结果的截图、视频或者录屏；如果是一个前端，也可以直接发上去。我把这些东西尽可能全地展示给受众，包括：
1. 它的路径；
2. 它用了多少时间；
3. 它用了多少 token；
4. 它是什么 effort；
5. 它加载了哪些 skill；
6. 它基于哪个 harness。
7. 以及还有其他能想到的各种要素

我的目的是，把产出的结果尽可能方便地展示给受众，而不是告诉受众这个一定是好的。我希望做到非常方便查看，受众不需要我给他指导，就能判断哪个好、哪个不好。


### 常见问题一：换模型

（这段是 AI 写的，还要调整）

模型肯定要换着测。一个行为在模型 A 上怎么调都调不出来，换到模型 B 上可能天然就有；也有一些 prompt，是为了补模型 A 的某个问题写的，换一个模型之后可能反而产生干扰。

所以换模型首先要看，在现在这套 harness 里，它会表现出什么样的行为。接下来才是决定要不要适配、适配到什么程度。比如你定义了复杂任务最后要交付一个文件，那有些模型很自然就会这么做，有些模型习惯在聊天里直接回答，你就得决定要不要把这个行为调过来。

但产品定义本身也可以变化。有时候新模型跑出来一种你之前没想到的效果，看起来确实更好，那也可以回头改产品定义，甚至让其他模型往这个效果上对齐。这里面没有一个永远固定的标准，还是要有人对最后的效果负责。

从评测角度，这两件事要讲清楚：直接换模型，能看到它在现有产品里的表现；分别适配之后再比较，能看到不同模型和 harness 组合起来的效果。后者里面已经包含了工程投入，把这个结果直接当成模型能力的高低，就会漏掉很多东西。

### 常见问题二：路径评测

（这段是 AI 写的，还要调整）

最后的产物相对好判断一点。文章写得怎么样，视频好不好看，代码能不能运行，都有比较具体的使用场景。但 Agent 的运行过程也会被人看到，用户可能会中途接管，可能想知道它现在在干什么，也可能只是想判断还值不值得继续等。

所以路径本身也是产品体验的一部分。一个任务最后做完了，但中间反复搜同样的东西，或者很久没有任何能让人理解的进展，用户的感受也可能很差。只评最后的结果，会漏掉这一部分。

难点在于，什么样的中间过程算好，这个事情没有那么容易定义。比如先做 plan，看起来是一个好习惯，但到底计划到什么程度合适？做一个很简单的任务也写一大篇计划，可能就让人觉得啰嗦。再比如工具调用次数少，看起来效率高，但也可能是少查了关键的信息。

我觉得这里要先把具体的问题讲清楚。你是在意用户能不能理解进展，还是在意它有没有浪费时间，或者需要定位它在哪一步把事情做错了？这些目的对应的评法是不一样的。直接规定一条标准路径，让所有 Agent 都照着走，很容易把一种实现习惯当成了能力要求。

这也是为什么运行路径值得保留给人看。很多时候你事先想不出一个合适的指标，但把几条路径放在一起，人就能看出其中的问题。再把这些判断里比较稳定的部分沉淀下来，比一开始就把每一步应该怎么做都规定死，要更容易往前推进。

### 常见问题三：商业决策

（这段是 AI 写的，还要调整）

评测能帮你看清楚效果，但最后上不上一个模型，还会涉及很多别的因素。比如成本、接入和维护的投入、公司是不是要求优先用自己的模型，以及一个新模型发布之后，用户对它有多强的预期。

假设一个模型热度很高，大家都想用，但在你的 Agent 里有几个场景表现不好，短时间内又调不完。这时候要不要先接进来，就是一个商业和产品一起做的决定。评测能提供的信息是，哪些地方不好、大概会影响什么用户、有没有其他选择。最后愿不愿意接受这些问题，还要结合其他要素去权衡。

只用自有模型也是类似的事情。它确实能减少需要适配的组合，还可以通过训练、微调去改模型行为，但这件事本身并不能证明最终效果会更好。它同时涉及公司的战略、资源怎么投入，以及模型这一层在业务里是什么位置。

所以看到一个产品的模型选择，不能直接倒推出它在技术上觉得什么最好。评测把效果和代价尽可能说清楚，商业决策在这些信息之上做取舍，这两层要能分得开。

## 如何跟模型打交道的 Mindset

我们前面把评测当成一个独立的概念讲了很多，现在社媒上不断冒出来各种独立的概念：prompt engineer、context engineer、harness engineering 等等各种新奇的功底。我觉得他们每一个词确实有独立代表一些思想，但是它们之间的交叉也非常多。

创造概念就是在创造抽象层级，好的抽象可以降低协作成本，所以造词儿这个事儿也就不是个坏事，这是提升生产力必须要有的流程，不然程序员们估计还在写汇编语言。 坏的地方在于，市场太热的时候从业者们会急着造词争夺话语权，大家创造出来的大部分概念完全不具备一层好的抽象应该符合的基本要素，像 skill，agent，harness 这些东西到底是个啥也说不清楚，用户和较真的从业者们一遇上了也一头雾水，本来是一个应该造福大家的事情，最后实际产生的作用也就只有 FOMO 到了老板们然后老板们折腾下面的人。

概念多了会让人绕进去，很多人被困在源源不断冒出来的新概念里，屏蔽了后面真正应该做的事。评测也好，harness engineering 等词也好，所有围绕模型的工作，我觉得都应该抽丝剥茧看到一个核心目的，就是让 AI 表现出符合自己设计目标的效果。

### 直接抄一个不行吗

最狭义的 Harness 直就是让 Agent Loop 能正确的跑起来和终止，再加上一些加载 skill，扩展 tool 等能力，这个部分里面的实现工作量并不大，搭一个并没有多大难度，或者直接基于 pi 或者 claude 或者 openai 的 agent sdk 封装甚至把一个已经跑的还不错的 agent 拷贝下来去魔改，这都不是很困难的事情。一个人一下午可能不能完全理解里面的思想，但至少可以讲明白里面有什么东西。

实际业务跑起来的时候，你会收到用户各种各样的反馈，每个人都会对 Agent 有各种效果上的要求。抄了之后，你得懂里面有什么，还得懂怎么改，又得有评测。不能抄过来就完全不变了。抄一个 Agent 框架内核解决不了这个问题。

evals 和 harness 设计和上一代的工作中的策略产品设计工作最类似，出题出指标就是把自己脑子里对于什么是好的给呈现出来，这个东西的 best practice 也跟做产品一样，就是先跑起来在说，很多效果优化项拍脑袋拍不出来，用什么麦肯锡方法论纸上谈兵也谈不出来，跑一遍看看效果才能想得出来哪儿好哪儿不好，才能发现出题，定指标和设计打分机制的灵感来源。

目前看到的唯一解就是有一个人了解模型+了解模型落地+了解产品+非常又责任心的超级大哥抱着享受探索未知领域的 mindset 去全盘负责这个事情，可想而知目前没有几个团队做得好这个事情。这不是人力/钱角度的难，这是一个伟大的为人类进步探索未知的任务！

## 引导普通人一起追求真理
除了专业的评测设计，还有一个 topic 我认为尤为重要，就是用户视角的评测，具体点说就是用户怎么样理解一个模型或者一个 harness 的能力以及表现出某种倾向性的原因。

这是在引导大众接近事物的本质，这是一个我内心一直追求的事情

### 我对现有广泛传播的评测的认知框架
现在大部分人，不只是用户，甚至包括专业从业者，也没有时间专门测试一个模型的表现。人们能看到的模型效果展示非常鱼龙混杂。

现在能接触到的 bench 分两部分。

第一部分是专业的 benchmark，每个模型发布的时候都会跑，有配套论文，他们在设立的时候定了很多指标，再通过一些论证去证明它合理，并且同时有社区不断反馈，可以在一些角度证明是相对公允的。

但这也给受众带来了很大的理解难度。像 Terminal-Bench、SWE 很火，大家都去在这个上面评测，受众会觉得它用的人多公允。但对于里面有什么题目、有什么东西，大家没有特别多的认知。

很多人对于专业 bench，最后只看个分数或者少数参数（比如分数+时间，可能这样就会忽略 token efficiency），那本身一个从多角度理解可以保障他公允的东西，经过了一次这种断章取义之后就失真了，一个相对公允的 benchmark 如果受众无法充分理解，那他的价值也会缩减很多。

第二部分就是社媒上各种效果展示，你也搞不清楚是不是 one-shot。很多时候较真一点的受众都会质疑，比如很多社媒上说是 Opus 5.5 做的视频，自己做一下就会发现，也就那么回事。

同时，社媒上也有针对专业 benchmark 进行包装的二次转播（比如非常带歪人对模型能力理解的斩杀线图），这也加剧了专业 benchmark 的评测能力在普通人心中的失真。
### 怎么引导人们
如上所述，现有的传播最广的两种 bench，到普通人面前往往都是误导

我想做一个东西，让没有那么多时间研究专业 benchmark 的人，也能理解一个模型大概有什么样的特征。
