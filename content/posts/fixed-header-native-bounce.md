做 Tabbit 文集的时候，我想调整一个很小的交互：主页和详情页的顶部栏一直固定在屏幕上，下面的书单和文章列表仍然可以滚动，到边缘时保留浏览器原生的橡皮筋回弹。内容从顶部栏下面经过时，还能透过半透明背景看到模糊效果。

这个需求来回改了好几轮。Agent 先关掉整页回弹，再给列表单独设置滚动容器，随后自己实现了一套弹簧动画。效果一直不对，我让它回退，又追问了一句：不能通过设置什么属性，让浏览器自动实现吗？

最后的方案很直接：**顶部栏使用 `position: fixed`，页面继续原生滚动，再给顶部栏预留与实际高度一致的占位。** 修改后，我在当前环境里体验了一遍，效果符合预期。

这篇记录具体怎么改，以及 Agent 为什么把一个小问题越改越复杂。

## 最初的问题：正常滚动时吸顶，边缘回弹时却一起移动

最初两个顶部栏使用的是 `position: sticky`。正常向下滚动时，它们会停在顶部，视觉上已经像是固定住了。但在当前 macOS、Tabbit 环境中，页面到边缘继续滑动时，顶部栏也跟着回弹。

这里需要把两个行为分开理解：一是元素如何定位，二是滚动到边界后浏览器如何反馈。

`sticky` 保留元素在正常文档流中的位置，并根据滚动祖先和包含块进行偏移。`fixed` 会脱离正常文档流，通常相对视口定位。因此，对“顶部栏始终留在视口上”的需求，应该先验证 `fixed`。这些定位规则可以查阅 [MDN 的 position 文档](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/position)。

本次观察到的 sticky 回弹表现属于具体浏览器环境下的结果，不能据此推导所有浏览器的所有 sticky 元素都会这样。排查时也不能只看到一个 `fixed` 就认定它一定相对视口：祖先上的某些属性，例如非 `none` 的 `transform`，可能改变它的包含块。

## 最终怎么改

最终版本是 0.3.20，主页和详情页复用同一个 `FixedHeader` 组件。内容仍然放在正常文档流里，由页面本身滚动。

结构可以简化成这样：

```html
<div class="fixed-header">
  <header class="header-surface">标题和操作按钮</header>
</div>
<div class="fixed-header-spacer" aria-hidden="true"></div>
<main>书单或文章列表</main>
```

顶部栏固定在视口上，背景层承担模糊效果：

```css
.fixed-header {
  position: fixed;
  inset: 0 0 auto;
  z-index: 40;
}

.header-surface {
  background: rgba(245, 243, 236, 0.92);
  -webkit-backdrop-filter: blur(12px);
  backdrop-filter: blur(12px);
}
```

这里的 `.header-surface` 是为了讲解统一使用的名字。实际项目里，主页背景层是 `.app-header-shell`，详情页是 `.collection-header`。

没有再设置禁止页面回弹的 `overscroll-behavior-y: none`，也没有把根页面锁成 `overflow: hidden` 后再嵌套一个列表滚动容器。列表可以从顶部栏后方经过，半透明背景上的模糊也就有了可以观察到的内容。

### 固定之后，要补上被移出文档流的高度

`fixed` 不占据原来的文档流空间。如果只改定位，最上面的内容就可能被顶部栏挡住。因此需要一个占位元素，高度与顶部栏一致。

顶部栏高度不能简单写死：桌面和窄屏的布局不同，标题可能换行，字体加载也可能改变尺寸。本次实现通过 `ResizeObserver` 同步实际高度，核心逻辑如下：

```tsx
useLayoutEffect(() => {
  const header = headerRef.current;
  const spacer = spacerRef.current;
  if (!enabled || !header || !spacer) return;

  const measure = () => {
    spacer.style.height = `${header.getBoundingClientRect().height}px`;
  };

  measure();
  const observer = new ResizeObserver(measure);
  observer.observe(header);
  return () => observer.disconnect();
}, [enabled]);
```

这段 JavaScript 只负责布局占位，没有监听 wheel 或 touch 来控制回弹，也没有计算弹簧速度和位移。滚动体验由浏览器提供。

项目还处理了两个已有使用场景：打印时恢复静态定位并隐藏占位；导出的独立 HTML 保留原有 sticky 顶部栏，使无脚本导出继续可用。这次 fixed 调整应用于交互页面。

## Agent 犯了什么错误

### 先关闭整页回弹，改变了原本想保留的体验

看到顶部栏跟着 bounce，Agent 最初在根页面上设置了 `overscroll-behavior-y: none`。顶部栏不动了，书单和文章列表的原生回弹也消失了。

这一步只解决了表面症状，没有完整保留需求。正确的验收条件应该从一开始就写清楚：顶部栏稳定、内容保留回弹、滚动经过背景时可见模糊，三件事需要同时成立。

### 过早拆分滚动容器，并高估了 CSS 属性的作用

下一步，Agent 锁住根页面，让书单和文章列表各自在内部容器里滚动，并设置 `overscroll-behavior: contain`。我实际体验后，发现内层列表没有预期的橡皮筋效果。

`overscroll-behavior` 控制滚动边界行为。`contain` 阻止滚动继续传递到祖先，同时允许当前容器的默认边界反馈；它无法保证每个浏览器、平台和滚动容器都提供相同的弹性效果。`none` 则还会抑制默认的边界反馈。具体语义见 [MDN 的 overscroll-behavior 文档](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overscroll-behavior)。

Agent 当时没有查明当前环境中内层回弹缺失的确切原因，就继续增加实现复杂度。独立滚动容器当然有适用场景，但这个需求应该先尝试保留现有滚动结构、只调整顶部栏定位。

此外，当列表被裁切在顶部栏下方的独立区域里时，内容从顶部栏后面经过的视觉关系也被改变，背景模糊更难呈现原本想要的效果。

### 太早接管了浏览器原生动画

原生回弹没有出现后，Agent 自己写了一个 `ElasticScroll`：监听滚轮和触摸事件，对内容做位移，再通过弹簧计算让内容归位。

这带来了更多需要处理的细节：触控板惯性、释放时机、连续输入、位移上限，以及嵌套滚动区域。那版实现把 90 毫秒没有新滚轮事件作为开始回弹的时机，每次新输入又重置弹簧速度，并把位移限制在 80 像素以内。

这些选择都可能影响手感。触控板在手指离开后仍可能产生惯性输入，事件间隔也不能直接代表用户已经松手。持续重置弹簧、碰到位移上限后的截断，都是需要进一步验证的潜在问题。

我们没有逐项隔离实验，无法断言某一个参数就是全部原因。但有一点已经很清楚：在尚未验证简单原生方案之前，Agent 就承担了整套回弹交互的实现成本。

### 把“能位移、能归位”当成了“手感正确”

当时的自动化检查确认了内容会移动、会返回，顶部栏位置保持稳定。这些只能证明部分代码行为符合预期。

用户真正关心的是连续的滚动体验：手指滑动时如何跟随，松手后如何衰减，到达边缘时是否自然。合成事件或普通滚轮测试不足以覆盖真实触控板的完整输入过程。

这也是一次验证目标选错的问题。测试围绕已经写出的动画展开，遗漏了最初要求保留的原生手感。

## 最后验证了什么

最终方案在桌面和窄屏尺寸下检查了主页、详情页：普通滚动过程中顶部栏保持在视口顶端，占位高度与顶部栏一致，没有横向溢出，详情页背景模糊仍然存在。扩展构建和已有的 16 项测试也都通过。

这些检查覆盖了布局和已有功能。随后我在当前环境里实际使用，确认回弹与顶部栏固定的组合达到了预期。两部分证据各自回答不同的问题，不能相互替代。

## 下次遇到同类问题，先做什么

先确认谁在滚动、顶部栏相对谁定位，再尝试最小修改：顶部栏改为 `fixed`，补上动态占位，保留页面原生滚动。然后用真实输入设备验证边缘回弹，同时检查窄屏、长标题和背景模糊。

如果最小方案仍然失败，再根据观察定位具体限制，决定是否需要独立滚动容器或其他实现。

这次最值得记住的是：Agent 很容易在一次修改不理想后继续加代码，逐步接管浏览器本来已经提供的能力。每增加一层实现，都应该回到原始需求重新判断必要性。尤其是滚动、惯性和回弹这类交互，原生行为本身就是产品体验的一部分。
