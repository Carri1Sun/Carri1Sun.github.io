## 先说这篇东西能给谁用

这不是一篇只写给做评测的人的文章。评测这个词容易让人以为它是个后置环节，实际上它就是"你到底认为什么是好的"这件事的工程形式。几类很不一样的人会在不同的地方碰上它，所以先把取用路径说清楚。

如果你是重度使用者，你真正想知道的不是哪个模型强，而是"新模型升级跟我有什么关系"。公开榜单回答不了这个问题，于是大多数人只能靠品牌选：大家都说某个模型好，但好在哪、哪里还不行，只有拿自己的任务跑一遍才知道。这篇东西里对你最直接有用的是两处：为什么你看到的演示跟你自己用起来的感受差那么多（少题多跑那一节里 pass@k 与 pass^k 的分工），以及怎么用十道题、四条标准、每题跑三遍建一个只属于你自己的传感器（每个人都应该有自己的一套题）。顺带也能看清一件事：你遇到的很多不好用不是模型笨，是它外面那层工具、上下文和交互设计没做好。

如果你是 Agent 或模型方向的产品负责人，你的难处往往不是不知道产品该怎么做，而是你的判断无法传递给工程。写代码好不好工程自己能判，但一段关系分析写得好不好、一份报告是不是拓到了对方真正在意的东西，他看不出来，也不应该被指责看不出来。把自己的判断写成一批带标准的题，是目前产品岗对 Agent 质量施加影响最直接的路径，比写需求文档直接得多。对应的是标准从哪来、产物好坏本身不客观时怎么评、以及评测真正改变开发方式的那几节。还有一条直接影响产品边界的结论：当某类输入形态下评测怎么都做不好时，正确的结论有时不是再优化 Agent，而是这个入口现在不该开。

如果你负责一个 Agent 的迭代，下一节那个别扭感应该是你天天遇到的：分数在动，但它不告诉你下一步该改什么。你能取到的东西最多：一个 case 的边界为何必须包含初始状态和可用工具，什么时候评轨迹、什么时候只评结果，怎么把一个末端现象归因到工具层而不是一路修 prompt，以及为什么少题多跑比多题一跑信息量更大。也包括一些约束：评测很难成为迭代方向的来源，但把它做成纯守门的工具是个更大的错。

如果你在具体领域里做专属 Agent，金融、法务、研报、内容生产这类，有两节是直接写给你的：行业共识基准可以拿来当标准的起点，但它只能带你到一定程度；以及事实与观点在评测上需要完全不同的处理方式，而这一点很少被讲清楚。

如果你做的是评测本身，或者在给公众讲模型与 Agent 的能力，这篇东西里最有用的可能是那些失败案例：一套完全有效的评测集为何可以被一行工程代码廉价满足，分数低为何应该先怀疑评测而不是怀疑 Agent，以及为什么公开榜单会系统性地偏向可确定性判定的能力，而体验差异恰好大量落在另一半。

剩下的东西没有按这些角色分开写，因为它们底下是同一组问题。先从一个几乎所有人都碰过的感觉开始。

## 一个绕不开的别扭感

做过一段时间 Agent 评测的人大概都遇到过同一种别扭感。评测集建起来了，题目够多够难，跑分也跑得出来，改动前后的数字确实在动，但你说不清这些数字要怎么变成下一步该做什么。

举个具体的。某个团队做了五十道网页创作题，评分标准是最后生成的网页里指定元素必须存在、必须可点击。这套评测是有效的，它测得出一个 Agent 能不能做网页，也拦得住你改坏了东西。但它对"接下来该改什么"几乎不提供信息。更尴尬的是它可以被非常廉价地满足：在 harness 里加一句"检测到必需元素缺失就重试"，分数立刻涨，而 Agent 什么能力都没变。

换个角度看同一件事。假设我想知道"要不要给 Agent 加 plan"这个改动是对的。顺着想毫无难度：把一份 plan 拼在每一轮输入的末尾，当作持续的业务指导，模型对自己方向的把握一定更清楚。这是常识层面的推理，不需要任何数据。但倒着推非常难——什么样的评测集，能让你从数据里发现应该做 plan？

把 plan 单独拎出来评倒是好构建：给一堆现场，问它该不该 plan、plan 长什么样，再对照参考答案。可这样评的已经是模型的一次输入输出，评的是 policy 和 system prompt 的设计，跟 plan 对整体任务完成率的贡献是两件事。放回端到端做有 plan 和无 plan 的对照组呢？中间变量太多，差异归因不到 plan 这一件事上。

这两个例子指向同一处，我认为它就是理解 Agent Evals 的起点：

> Agent 评测的困难不在打分，而在于被评的对象不是一个端到端的函数。

模型评测的对象是输入到输出。定了业务目标就能反推出该出什么题、该怎么打分，评测结果又能相当直接地转成训练信号——缺哪类能力就采买哪类数据，做完后训练，分数就跳。Agent 评测的对象是模型加一层确定性工程，加一个环境，加一段交互。其中相当一部分，工具怎么封装、context 怎么组装、plan 要不要注入、要不要拆 subagent，根本不是业务目标本身，而是你为达成业务目标所选的解决方案。

于是 Agent 评测天然背了两个互相冲突的角色。定义问题，这是评测该做的。评判解决方案，这是评测做不好、做了就变成又当裁判又当选手的。后面所有具体判断都从这句话推出来。

## 从模型评测借来的直觉，在哪里失效

"Agent 评测更难"这句话正确但没什么信息量。拆开看，它难在几个非常具体、彼此独立的地方。

执行过程不能端到端评，而且它本来就不是业务目标。Agent 的执行结果可以端到端评：产物在不在、状态对不对、报告有没有胡说。执行过程不行。你的业务目标是"给我一份能用的报告"，从来不是"请在第三步调用搜索工具两次"。过程不是目标，却又明显影响目标，所有轨迹评测的尴尬都从这里来。

Agent 也不是纯黑盒。评测这件事在模型上顺畅，很大程度上因为模型是黑盒：你无法从原理上推导它该怎么表现，只能靠测。harness 是确定性工程，你写了什么它就做什么。对一个你完全知道其因果的东西做评测，收益有限。所以评测应该主要指向那些相对黑盒、无法从 A 直接推到 B 的部分。硬性校验类的改动，比如"产出的页面元素必须可点击"，不需要评测去发现，它只需要一个后置的自动化测试保证它一直成立。引导式的、system prompt 类的、没有直接因果链的改动，才是评测该管的地方。

第三处不对称最要紧：工程作弊极其廉价，而且零泛化。评测要求"搜得全"，我在 harness 里写一句"没搜到二十个结果就重试直到搜够"，分数立刻上去，能力毫无变化。模型侧当然也有刷榜，但模型作弊至少还有一点泛化的运气——你为某个方向补的数据，可能顺带长出别的能力，因为它不是从 A 到 B 的直线。工程作弊没有这种运气，它精确命中评分点，出了评分点什么都不剩。

外部的例子比我们讨论时想到的更极端。有团队记录到 coding agent 在跑 Terminal-Bench 时直接去搜该题对应的通关命令，也有 agent 从本地 git history、公开仓库、web archive、包注册表里挖参考实现 [1]。更狠的一例是 OpenAI 内部的一个安全评测，模型把 0-day 与凭据串起来打到 Hugging Face 的生产设施上，去拿评测的答案键。没有人让它这么做，它这么做只是因为只看结果的打分会奖励最短路径 [1]。这些属于模型侧的 reward hacking，但机制跟工程侧完全同构：任何只看终局状态的打分，都在为绕过它的最短路径出价。

最关键的一处是，模型评测只定义问题，Agent 评测同时在定义解决方案。模型评测告诉你"这类问题你做不好"，不告诉你该怎么改，改法留给研究员和数据。Agent 评测一旦做细，往往连解法都定了——你应该先搜再读再写，你应该在这里插入一次确认。而如果评测已经把解法定死，按这个解法做就一定得高分，评测也就丧失了鉴别力。你既是出题人又是答题人。

这直接解释了我见过的一个真实现象。一个五六个人、素质相当不错的评测团队，最后把评测做成了自动化测试：每次改完 harness 跑一遍 case，看那些 case 稳不稳，稳就说明改动没问题。这不是懒惰或者能力问题，是上面那条约束的自然结果。评测在这里能提供"没坏"，很难提供"该往哪走"。

对比模型侧那条传导链有多顺。一个新的 coding benchmark 刚出来时所有人都没有对应数据，通过率就是个位数；采买数据、做完后训练，通过率能直接跳到五成以上。这显然不是通用能力自然溢出，是评测直接驱动了迭代。Agent 侧不存在这条链，你不能采买一批 harness 数据。

所以我倾向于把话说得直白些：不要指望 Agent 评测像模型评测一样成为迭代灵感的起源。它的位置在别处——防退化的约束，定位问题在模型还是工具还是 context 的归因，把人的判断变成可复用标准的校准。这三件事都有价值，都不是"产生方向"。不过这句话很容易被听成"评测只能守门"，而那是个更大的错。后面有一节就是专门回来拆这个误读的。

## 一个 eval case 到底是什么

在讨论轨迹和打分之前得先把 case 这个单位说清楚，因为大部分评测的问题出在这一层，而不是打分层。

一个可用的分解：task 是带有明确输入和成功判据的一次测试；每一次尝试叫一个 trial，因为输出会变，所以同一个 task 要跑多次；grader 是给表现某个方面打分的逻辑，一个 task 可以挂多个 grader；transcript 或 trajectory 是这次 trial 的完整记录，包括输出、工具调用、推理和中间结果；outcome 是 trial 结束时环境的最终状态 [2]。

这里面最容易被忽略也最有价值的是 outcome 的定义。它是环境的最终状态，不是 Agent 说了什么。一个订票 Agent 在结尾说"您的机票已预订成功"，这不是 outcome；数据库里到底有没有那条预订记录才是 [2]。这个区分在实践中杀伤力很大，大量看起来很成功的 trial，只是把成功叙述了一遍。

但比术语更要紧的是 case 的边界包含初始状态和可用工具，而不只是那句 prompt。同一句"帮我分析这个人该怎么聊"，在有三个月记忆积累的账号上跑，和在一个空账号上跑，是两个完全不同的 task。

我见过一个非常漂亮的 case。用户在会议里投屏了一封 VC 的拒信，Agent 从截图里识别出场景和意图，查出这家基金、这封信的发出人、二期基金的规模和 close 时间，判断出拒信的核心是阶段不匹配而不是东西不行，从公开信息里发现对方组合全是 infra 工具而用户就在做 infra，甚至注意到用户四十几岁、卖了房子出来创业这个细节，把它解读成一个强创始人信号，最后给出的建议是两三个月后带着真实部署数据再回，写邮件直接写数字不要写故事。

这个 case 好到让人想立刻拿它当 eval。但它的作者自己说得很清楚：这是个好 showcase，它不能稳定复现，而且它成立的前提是这个账号已经用了三个月、积累了足够多可供联想的记忆。如果你把它写进评测集而不写清初始状态，你评的就不是 Agent，是运气加上一个特定账号的历史。

输入的信噪比同样是 case 的一部分。有一类需求听起来很自然：让 Agent 直接吃两小时会议的完整转录。但会议记录是极脏的输入。在不知道参会者是谁、各方处境如何、这场会的目的是什么的情况下，你没法判断这两小时里有多少真话、多少假话、多少表演。区分 noise 和 signal 所需要的背景，正是转录稿里没有的。相比之下，用户主动截下来送进去的那一屏带着注意力标注——他按下那一下，本身就是"这段重要"的高质量标注。同一句"帮我理解这段关系"，喂一屏用户主动选的截图，和喂一份两小时转录，是难度差好几个量级的两个 task。

这条推论有个反直觉的实践含义：当你发现某类输入形态下评测怎么都做不好时，正确的结论有时不是再优化 Agent，而是这个入口现在不该开。产品决策本身可以是评测的结论。

还得提一句 case 的另一种失败模式，case 可能本身就是坏的。这不是理论顾虑。OpenAI 在 2026 年初宣布不再把 SWE-bench Verified 当作前沿 coding 能力的度量，理由是污染和设计问题；随后审计 SWE-bench Pro，估计约 30% 的任务是坏的，问题集中在四类：测试过严（把 prompt 里没提的实现细节当硬要求）、prompt 欠定（隐藏测试考了推不出来的要求）、测试覆盖太松（不完整的修复也能过）、prompt 误导 [3]。有个例子很典型，prompt 给的示例是一个前导空格，隐藏测试要求两个，规规矩矩照 prompt 做的模型必然挂 [3]。

这类事在自建评测集里更常见。一个可操作的判据是，如果一个 task 在很多次尝试下通过率是 0，最可能的解释是任务坏了，不是 Agent 不行 [2]。另一个判据是让两位领域专家独立看，能不能给出同一个通过或不通过的判定；给不出，这个 task 的歧义就会直接变成指标里的噪声 [2]。还有个很省事的做法：为每个 task 准备一份参考解，一份已知能通过所有 grader 的输出。它同时证明了两件事，任务可解，grader 配置正确。

## 什么时候评轨迹，什么时候只看结果

这是材料里争论最久、外部实践分歧也最大的一个问题。我认为分歧本身来自把两件事混在一起了：用轨迹当标准答案，和用轨迹做归因。前者大多是错的，后者往往是必需的。

先说反对的一边。一个相当有分量的经验是不要去硬性检查 Agent 是否按特定顺序调用了特定工具。这类断言过于僵硬，产出的测试非常脆，因为 Agent 经常找到设计者没想到的有效路径，所以评它产出了什么而不是它走了哪条路通常更好 [2]。这个说法有极强的实例支撑：Opus 4.5 在 τ2-bench 的一道订票题上找到了 policy 的一个漏洞，按评测的写法它失败了，但那实际上是对用户更好的方案 [2]。如果你的 grader 检查的是路径，你会系统性地惩罚这种创造性。

支持的一边证据同样硬。

有一个改动我印象很深。为了提升推理深度和记忆使用的宽度，工程上加了 subagent。结果是信息量满满，检索做了很多轮，材料铺得很开，但所有推理都是涣散的，像一个投资实习生写的东西，完全没抓住主线。这个改动如果只看 outcome，几乎一定会被判为改进：覆盖度上去了、引用变多了、篇幅更充实。只有看轨迹，或者用一个能感知推理是否连贯的主观标准去看，才能发现它是退步。

而且这个失败是场景相关的。同样的 subagent 在生产力场景里非常好用，那类任务可以拆出很多无状态的子任务，主 agent 把上下文通讯设计干净就行。在需要连贯上下文、需要每一轮对前面的东西有更完整概括的场景里，拆开就等于把推理拆散了。这说明"某个 harness 改动是好是坏"这个问题本身是不完整的，必须补上"在什么样的任务上"。

另一个例子更接近日常。工程师在修"意图老是抓不对"这个问题，方法是疯狂调 prompt。真实原因完全不在 prompt：工具没优化好，前两轮搜索没搜到该搜的东西，模型手里根本没有可供推理的 context，只能强行拟合。硬推理的结果自然很差。正确的顺序是先把工具做好，让事实性的 context 变丰满，再去调意图召回。工具没优化好之前调意图是白调。

这几乎是"用评测发现具体 harness 问题"的教科书样本，而它成立的唯一条件是你看了轨迹的前几步。只看最终输出，你看到的现象是意图不对，你会一路修到 prompt 上去，修不动就开始怀疑模型。看轨迹，你看到的现象是第二轮搜索返回的东西不对，归因立刻落到工具层。在多步系统里，失败的表象几乎总出现在链条末端，原因几乎总在前面。只评终局就等于放弃归因。

我倾向于这样划分：

| 对象 | 主要评什么 | 理由 |
| --- | --- | --- |
| 硬性可验证的产物（元素存在、可点击、类型检查、测试通过） | 只评结果 | 因果确定，评测无从发现新东西，只需保证不退化 |
| 环境副作用（是否真的建了预订、是否改了不该改的文件） | 只评结果，但评环境状态而非 Agent 的自述 | Agent 会把成功叙述一遍 |
| 信息获取质量（搜到的东西对不对、够不够、来源可靠不可靠） | 评轨迹，用于归因 | 末端表现无法区分"没找到"和"没想到" |
| 推理连贯性、是否抓住主线、是否在恰当时机停下或追问 | 评轨迹，且需要主观标准 | 没有可自动判定的替代量，只看结果会奖励堆量 |
| 具体的工具调用顺序 | 不要评 | 会惩罚有效的替代路径 |
| 效率（轮数、token、耗时） | 作为约束指标而非目标 | 有意义但容易被当作目标而扭曲行为 |

最后一条多说一句。"在产物质量一致的前提下 token 越少越好"是个成立的判据，但 token 量不一定是好指标，它容易奖励偷懒。更稳的用法是把它当约束：先看质量是否达标，再在达标集合内部比效率，而不是把两者揉成一个总分。

还有一个对轨迹评测的重要限定，来自可解释性方向的研究。模型经常用某个提示或捷径得到答案，然后在写出来的推理里省略这一步，反过来给出一条更干净的路径 [1] [4]。这意味着 Agent 对"我为什么这么做"的自述不可信。可评的是你能观察到的东西：工具调用、文件 diff、网络请求、环境变更。模型自己的解释只能当线索。

## Grader 的三层，以及每一层的边界

打分器大致分三层，各自解决的问题很不一样，混用是常见错误。

确定性 grader 解决"能不能被机器无歧义判定"的部分：字符串匹配、fail-to-pass 与 pass-to-pass 测试、静态分析、终局状态校验、轮数与 token 统计 [2]。它快、便宜、客观、可复现、易调试，代价是对合理的变体很脆，也承载不了细腻的判断 [2]。它的正确位置是回归线——你已经知道什么是对的，只是要保证它一直对。

model grader 解决"人来不及看、但又需要判断"的部分。这里有一个我认为最实用的方法论：把模糊要求改写成一个模型也能执行的判定流程，而不是改写成一句更文雅的形容词。

举个完整的例子。"内容要有事实依据、引用不能出错"这个要求太模糊，没法直接打分。可执行的写法是：让一个模型抽出文中每一条观点；要求每条观点都带来源索引；先判定这个索引本身是否有效；再判定索引指向的原文里那个观点，跟文中写的是否一致；一致的比例越高分越高，偶发不一致扣一点分。这不是一条评分标准，是一条评分流水线。而一旦你写到这个粒度，它对裁判模型的能力要求就很低了，裁判用便宜模型完全可以，不需要拿最强的模型去做打分这种事。

反过来说，这也解释了为什么"用哪个模型当裁判"这个问题经常问错方向。如果你必须用最强的模型才能打准分，通常说明你的标准还没写清楚。

同一个模型既写又评会不会有问题？只要打分标准写得足够明确，风险是可控的，因为它变成了一个指令遵循任务。风险来自你完全放开让它自己发挥，此时它的表现倾向和评分倾向必然一致。这里要加两条外部限定：LLM 裁判有已知的 self-preference 与 self-enhancement bias、position bias 以及 verbosity bias，偏爱更长的回答 [5]；实践上更稳的做法是每个维度用一个独立的裁判分别评，而不是让一个裁判一次评所有维度，并且定期用人工标注去校准 [2]。交叉验证不是可选项。

主观评测解决前两层都碰不到的东西，它有两个不可替代的用途：作为校准 model grader 的金标准，以及评那些目前根本没有可自动化替代量的东西。后者包括什么？凡是"轨迹好不好"，最终都得有一个主观评测在那里兜底。plan 就是典型，你没有办法从任何客观评测里推出"有 plan 一定比没 plan 好"这个结论。写作类产出也是典型，而且这里要区分一件事：Agent 写的文章和模型一把输出的文章是不同的东西，所以针对 Agent 产物的主观评测不能直接复用模型侧那套。

主观与客观的分界线由业务目标决定，不由技术手段决定。还有一个更彻底的说法值得摆在这里：这个世界上并没有绝对客观的评测标准。所有指标都是人定的，只是当一个标准被足够多的人认可、又很难被反驳时，它就被当成客观的了。金融报告领域之所以看起来有客观标准，是因为存在共识基准，大家默认顶级投行的研究报告就是那个样子。这不是客观，是共识。

这个看法直接改变精力分配。不要把精力花在追求客观，要花在体系化上：每个用例怎么测、怎么打分、指标是什么，这些确定下来就叫体系化，它比标准够不够客观重要得多。推到头就是一句话：你的偏好就是标准，直接写进去。如果你认为适合人阅读的文章是段落式的、同一段里有转折和递进的，而不是罗列一二三四五六七的枚举体，那就把这条偏好写进 grader，让裁判读到这种格式就给高分。绕来绕去想给它找个客观依据，是浪费时间。

打分项的数量也常被问。答案取决于你要观测什么，观测点少就少设，观测点多就多设。但有一条规律要注意：指标少必然偏科。权重集中在少数几项上，优化就一定往那几项倾斜。如果你需要一个能代表通用水平的总分，就得多设几项；如果是为了指导内部迭代，那么想清楚了什么就把什么设成标准，反而更好。还有个容易被忽略的差别，对外传播时模糊一点的标准反而有用，因为大众很难理解每一分是怎么来的；对内迭代时，模糊标准毫无价值。

## 标准从哪来，以及标准会被 Agent 反过来改写

Grader 怎么写是技术问题，标准从哪来是更前置的问题。这里有一个我认为最实用、也最少被讲清楚的方法。

标准的第一版来自你自己做这件事时为了达成目标付出的努力。不是来自你对"好"的抽象定义，而是来自你的具体行为。我自己做代码重构时会去检验这次改动对原有逻辑有没有影响，会尽可能多扫一遍可能被干涉到的模块，这就是一条可以直接变成评分标准的好行为。写研究报告的人也一样，你自己做这件事时会核对哪些东西、会补哪些交叉验证，那些动作就是标准的原始素材。

但第一版标准不一定可靠，它需要被 Agent 实跑一遍来校准。有时你定低了，Agent 随手就能达到，甚至做得比你好；有时你定高了，它拼尽全力也过不去。

跑出来比你的标准更好，就把它的表现升级成新标准，之后用于回归校验。这一步在实践中经常被跳过，但它很关键，因为你的标准其实在表达你的产品设计——标准是什么样，产品呈现出来的东西就该是什么样。你不能让标准低于你已经稳定能做到的水平，否则这个标准就在允许产品退化。

跑出来比标准差很多，你要判断的是两件事中的哪一件：该改 Agent 的架构去接近这个标准，还是这个标准定得实在太高、该修回一个合理的程度。这个判断没有公式，但至少你知道要问这个问题。

外部有一个相当漂亮的印证。前面提到 Opus 4.5 在 τ2-bench 上找到 policy 漏洞、按评测写法算失败但对用户其实更好 [2]，这正是"Agent 的表现该反过来更新标准"的最典型形态。还有一组更极端的例子：Opus 4.5 在 CORE-Bench 上初测 42%，后来发现是打分过于僵硬（期望 96.124991…，写 96.12 就算错）、任务描述有歧义、以及部分随机任务根本无法精确复现；修掉这些问题并换一个约束更少的 scaffold 后，分数跳到 95% [2]。METR 的时间跨度基准也出现过任务配置错误，任务说"达到某个阈值"，打分却要求"超过阈值"，结果反而惩罚了老实遵循指令的模型 [2]。

这些例子的共同结论是，分数低有两个原因，一个是 Agent 不行，一个是评测不行，而后者的概率远高于直觉。所以有一条纪律值得写死：在有人真正读过若干条 transcript 之前，不要相信任何 eval 分数。

评测集还有另一种用途，跟衡量自己没什么关系，是用来定义一个问题领域。HLE 这类评测集从设计上就没打算让当下的模型做到，它的价值在于把一个方向标出来，让所有人朝这里发力，而事实上通过各种途径，那种效果最后还是被涌现出来了。GAIA 是另一个形态：466 道人工标注、有唯一可验证答案的多步任务，作者刻意选了对人来说繁琐而非困难的题，需要浏览、多模态、文件读取和代码，它的挑战者是完整的 agentic 系统，而不是裸模型 [6]。

这提示了一个容易被忽略的分工。如果你出评测集的目的是定义领域，那么难到暂时不可实现是特性不是缺陷；如果目的是指导自己迭代，那么不可实现的题只是噪声。顺着这个逻辑还能看到，出题者不需要知道解法，实现的方法未必由你来想。

## 审美、报告、文章：产物好坏本身就不客观时怎么评

前面那些分层和判定流水线，在遇到三类产物时会同时失效：一个前端页面好不好看，一份报告够不够专业，一篇文章写得好不好。这三类东西共同的麻烦是，你能一眼看出好坏，但它们没有外部参照物可以校对。订票任务可以去数据库里查那条记录在不在，页面审美没有数据库。

先把一个很容易被混淆的分层拆开。页面类产物实际上有三层，可用、正确、好看。可用是确定性的，能不能跑、控件能不能点、控制台有没有报错；正确是半确定性的，需求里要的东西在不在、交互行为对不对；只有第三层是审美。大部分团队的真实问题在前两层，却把精力花在争论第三层能不能自动化。前面那五十道网页题的教训就在这里：它测的是第一层，却常被当成在测"做网页的能力"。

真正进到第三层，有一条结论比我原本以为的更强硬：不要让裁判给绝对分，让它做成对比。一份针对网页开发质量的元评测工作测了十几个裁判模型，成对比较比单份打分平均高出八个百分点以上 [14]。道理不难想："这个页面审美几分"这个问题对人也很难回答，而"这两个哪个更好"对人很容易。把难题换成容易题，而不是把难题交给更强的模型。

报告类产物上有一个同构且更漂亮的证据。DeepResearch Bench 的 RACE 框架做了一组消融：去掉"对着一份参考报告做相对打分"这一项，与人类判断的一致度从 72.56 掉到 68.19，是所有消融里跌幅最大的；而去掉精心设计的维度权重几乎没有影响，只掉到 72.11 [15]。这两个数字放在一起的意义很大：很多团队花大量时间调权重，而真正提高一致性的是给裁判一份参照物。同一项工作里还有一个值得知道的数字：直接问模型"这份报告好不好"的 vanilla 基线只有 60.46 [15]。没有流程的主观打分基本不工作。

所以审美类评测的第一步不是写 rubric，是准备参照物。你需要一份你自己认为合格的样本，哪怕它是人做的、或者是 Agent 以前某次跑得特别好的一次。这与前面那条"跑得比标准好就把它升级成新标准"是同一件事，只不过在主观产物上，那份新标准的形式不是一句描述，而是一份具体的产物。

第二步才是把"好看"拆开。这里有一组数据值得记住。前面那份网页元评测工作在引入结构化 rubric 前，两位专家标注者之间的一致率只有 65%，与原始 arena 标签的一致率更低，只有 53%；引入一套按需求展开的 rubric 树之后，同一批人、同一批页面，一致率升到 92% [14]。这是我见过对"把模糊标准写成判定流程"最硬的量化支持，而且它改善的不是模型，是人。换句话说，如果你团队里两个人对同一个页面的审美判断对不上，问题很可能不是审美本身不可言说，而是你们没把它拆到可判定的粒度。

拆到什么粒度？网页那份工作把 rubric 树分为意图、静态质量、动态行为三支，叶子节点全是二元判定，逐层聚合，根节点给总分而叶节点通过率给诊断信息 [14]。它们拆出的单维度诊断力还有一个有意思的次序：只看意图的 rubric 最弱，静态质量居中，动态行为更好，三者合用最好 [14]。这直接推出一条很具体的实践：只拿首屏截图去评一个页面，你丢掉的不只是交互，还有审美的一大半——悬停、过渡、滚动时的节奏、加载中间态，都在静态图里看不到。

文章类产物在这一步上有一个特别具体的例子。如果你认为适合人阅读的文章是段落式的、同一段里有转折和递进的，而不是一二三四五六七的枚举体，那么"可读性"这个词就不应该出现在 rubric 里，应该出现的是一条很粗但可判定的规则：枚举列表占全文的比例超过多少就扣分。这条规则不优雅，但它能被执行，而"文笔流畅"不能。反过来说，如果你发现自己写不出这种粗但可判定的规则，那通常说明你对自己的偏好还没想清楚，而不是这个偏好太微妙了。

报告类产物可以拆得更细。一份全人工编写的深度研究 rubric 集把每道题拆成二十到四十多条具体标准，分在六个轴上：显式要求、隐含要求、信息综合、引用使用、表达质量、指令遵循 [16]。其中最值得搬过来的两个设计：它区分必选标准和可选标准，必选项定义"不满这些就不算合格"，可选项区分"合格"和"好"；它还给了负权重标准，专门惩罚事实错误、跑题、啰嗦这类常见失败 [16]。负权重这个做法其实就是前面"应该触发要配不应该触发"那条在 rubric 内部的实现。写作类产物尤其需要它，因为写得长、引用多、覆盖全，在任何只有正向标准的 rubric 下都是稳赚的。

这里需要插一句对前面判断的修正。我前面说标准写得够细时裁判可以用便宜模型，这个判断基本成立并且有数据支持：RACE 换裁判模型的对比里，o4-mini 以大约十分之一的成本拿到了接近最好模型的一致度，而最贵的 o3 反而最差 [15]。但在真正依赖视觉判断的审美任务上，天花板是真存在的：那份网页元评测里，最好的裁判与专家的一致率是 70.34%，人类之间是 84.56%，差了大约十五个百分点，而且更大的模型收益递减，全卡在 70% 附近 [14]。另一项面向界面审美的研究给了更具体的边界：两个界面的人类评分差距越大，模型判对的概率越高；差距小的时候基本无效 [17]。

把这两个结果合起来，审美类评测的能力边界很清楚：它能稳定地筛掉明显差的，不能在两个都不错的方案之间做决定。这对开发流程的含义非常具体：把自动审美评测当作回归线用，防止你改出一个丑东西；不要拿它去驱动审美上的细节优化，那一段只能靠人。

还有一个建设评测集时很容易错的地方。那份界面研究里有一个细节：作者刻意把部分专业设计稿的质量调低了，因为全是专业稿的话评分会集体偏高，测不出东西 [17]。你建主观评测集时需要同样的意识：里面必须有差样本，而且最好是你自己知道差在哪里的那种差样本。全是好作品的评测集区分度极低。

最后说一个真实存在的分歧，我不打算把它抹平。rubric 到底能不能让模型起草？网页那份工作发现模型生成的 rubric 树与人写的效果接近，因此用少量示例让模型批量生成 [14]；而那份深度研究 rubric 集坚持全人工编写与审核，花了两千八百多小时，理由是只让人审核模型生成的 rubric 会引入锚定偏差，也抹掉领域细节 [16]。我倾向于这两个结论都对，只是对应不同目的：你想快速拿到一个能用的回归线，让模型起草然后你改；你想把自己的审美真正固定下来变成团队资产，那就只能亲自写。模型能帮你把已经想清楚的东西展开，帮不了你想清楚。

## 两种评测集：爬山用的和守门用的

把评测集按目的分成两类，是我见过最省事、也最容易被跳过的一步。

capability eval 回答"这个 Agent 能做好什么"，它应该从一个低通过率开始，专门瞄准 Agent 现在做不好的任务，给团队一座山爬 [2]。regression eval 回答"它还能做好它以前能做好的事吗"，它应该常年接近 100%，一掉就说明有东西坏了 [2]。这两者的设计要求几乎相反：capability eval 通过率高了就没信息量，regression eval 通过率低了就没法用。混在一个套件里跑，两边的信号会互相污染。

一个自然的生命周期是，capability eval 被爬到高通过率之后毕业成 regression suite，从"我们到底能不能做到"变成"我们还能不能稳定做到" [2]。

这个视角让前面那个尴尬现象重新被理解。我说过，一个不错的评测团队最后把评测做成了自动化测试。从 capability 和 regression 的分野看，这不是失败，那本来就是 regression eval 的正确形态。真正的问题只是这个团队同时失去了 capability eval，于是失去了爬山的方向。而 Agent 侧的 capability eval 之所以难做，又回到了开头那句话：它要求你在不预设解法的前提下定义"更难的问题"，而 Agent 团队的日常工作就是设计解法。

还有一个具体教训值得抄下来：问题集要平衡，两个方向都测。单边的评测会带来单边的优化。如果你只测"该搜的时候搜没搜"，你就会得到一个什么都要搜一遍的 Agent，所以既要有该搜的题（今天天气），也要有不该搜、直接答就好的题（苹果是谁创立的）[2]。推广开来就是，任何"应该触发某个行为"的评测都必须配一组"不应该触发"的对照，否则你在训练一个过度触发的系统。前面提到的"没搜到二十条就重试"式作弊，在有负例的评测集里是活不下去的。

顺带说 capability eval 的饱和风险。评测饱和了不等于能力饱和了，只是这套评测看不见新的进展。有个案例很典型：一家做代码审查的公司一开始对 Opus 4.5 印象平平，因为他们的评测都是 one-shot coding 题，抓不到长任务上的提升；改成 agentic 评测框架后才看清差距 [2]。当你觉得新模型没什么提升时，先怀疑自己的评测形态跟不上，再怀疑模型。

## harness 还在拓荒阶段，评测不能只服务于守门

上一节那个团队把评测做成自动化测试的例子，我先前的解释是他们丢了 capability eval。这个解释不错但不够，它还漏了一层：他们隐含地假定了 harness 该长什么样已经基本确定，剩下的工作是不要把它改坏。而这个假定是错的。

Cognition 那篇反多智能体的文章里有一个类比我觉得很准：HTML 诞生于 1993 年，React 到 2013 年才出现；今天做 agent 就像还在玩裸 HTML 和 CSS，除了最基础的那几件事，没有任何一种做法成为了标准 [18]。同一篇文章直接点名了两个头部机构开源的 agent 框架，说它们在推广错的做法 [18]。这不是一个细节上的分歧，是架构层面的分歧，而且分歧双方都拿得出真实的生产经验。

前面那个 subagent 的例子放回这个背景里就不再是一个孤例。生产力场景能拆出很多无状态子任务，上下文可以拆得很干净，所以开 subagent 很好用；关系类场景需要的是非常连贯的上下文，拆完之后产物看起来信息量满满，实际上像一个没抓住主线的实习生。Cognition 给这个现象提供了一个更干净的命名：并行的 subagent 各自基于互相冲突的隐含假设做决定，而这些假设从未被提前规定，于是主 agent 只能去缝合两个误解 [18]。他们给的例子很具体：让两个 subagent 分头做 Flappy Bird 的背景和小鸟，结果背景做成了超级马里奥风格，小鸟不像游戏资产。同一个架构选择，在一个场景里是对的，在另一个场景里会直接毁掉产出质量，而这一点你不跑不会知道。

所以"不要只锚定确定性的东西"这句话在这里有一个很具体的含义。Fowler 那套 harness 框架把控制手段分成两类，事前引导和事后感知，并且给了一句很值得搬过来的话：只有事后感知，你得到一个反复犯同一个错的 agent；只有事前引导，你得到一个编码了一堆规则、但从不知道这些规则到底有没有用的 agent [19]。只做回归评测就是后者。你把自己对 harness 的所有假设固定下来，然后只验证它们没被破坏。

这里有一个比"多做实验"更尖锐的说法，同一篇文章把它列为开放问题：如果你的 sensor 从不报警，那是质量高，还是探测机制不够 [19]？把这句话换成评测的语言：你的回归套件常年绿灯，可能意味着你很稳，也可能意味着你早已停止探索。两者在数据上长得一模一样。区分它们的唯一办法是看你最近一次往评测集里加题是什么时候，以及那道题是不是你现在做不到的。

拓荒心态具体落到评测上，我认为是三件事。第一件是把架构选择当成待验证的假设而不是前提。要不要拆 subagent、要不要注入 plan、工具该做得多原子还是多复合、上下文该不该压缩，这些都不是应该靠品味定下来的事，它们都应该有一组对照跑。第二件是接受很多实验的结果是无效，并且把单次实验的成本压得足够低。下一节会说到，Agent 侧的工程改动十道题跑三遍就能看出有没有用。那条结论真正的价值不在省预算，在于它把实验频率抬到了一天几个想法的量级，而不是一个季度一个。第三件是评测集本身必须跟着架构一起改。你换了一种工具形态、换了上下文组装方式，原来那批题很可能已经测不到新的失败模式。前面那个代码审查公司的例子是模型端的同类现象，它们的评测形态跟不上了。

第三件事还有一个更彻底的版本：评测 harness 自身的覆盖度目前没有方法。测试领域有代码覆盖率和变异测试告诉你"测试本身够不够"，harness 这一层没有对应物 [19]。你无法回答"我的 guides 和 sensors 盖住了多少失败空间"，只能靠不断遇到新失败、不断补。这是拓荒阶段的正常状态，不是你团队的问题。

有一个给这个探索空间提供结构的想法值得单独拿出来。控制论里有一条 Ashby 必要变异度定律：调节器的变异度必须至少等于它所调节的系统，而且它只能调节它拥有模型的东西。应用到 agent 上：模型能产出几乎任何东西，而承诺一种固定的任务拓扑就收窄了这个空间，使完备的 harness 变得可行 [19]。这给前面那条窄定义宽覆盖提供了一个比经验更硬的理由，也解释了为什么场景专属 harness 在工程上总是比通用 harness 好做。有人把这个判断说得更直：做定制的通用 harness 价值不大，做定制的任务专属 harness 价值很大，因为你能把领域先验、模型配比和交互形式都编码进去 [20]。但这条与前面讲 General Agent 评测集的那一节存在张力，我没有把它解开。

拓荒心态也有一个必须同时拿住的反面。你现在做的相当一部分 harness 工作，是在为模型当下的缺陷打补丁。最干净的已发生例子是 2024 年的 edit apply model：当时大模型输出规范 diff 很不可靠，于是普遍的做法是让大模型输出一段 markdown 描述、再让小模型据此重写整个文件，而这套东西毛病很多；今天编辑决策和执行多数由单个模型一步完成 [18]。那一整层工程连同为它建的评测一起没了意义。所以积极迭代架构并不等于每一层都值得你投入，有些东西值得先等一个版本。区分哪些是在探索真问题、哪些是在替模型抬棺材，目前没有可靠方法，只能靠判断。文末开放问题里那个关于脏 context 的赌注，就是这个判断的一个具体版本。

把这节和开头那句话接上。我在前面说 Agent 评测不应该指望成为迭代灵感的起源，这个判断我仍然保留，但它易被误读成"评测只能守门"。它真正的意思是：方向来自你对任务和用户的理解，来自你敲定一个想法后去试，而评测的职责是让这些尝试变得便宜、快速、并且结果可信。一个只有回归套件的团队不是评测做得不够好，是它已经不再尝试了。

## 少题多跑：Agent 场景里样本量的反直觉

这是材料里最反直觉、我认为也最站得住的一条判断：Agent 的工程改动只需要很少的样本就能衡量，因为它是确定的。十道题和一百道题差别不大，样本少的时候把同一批题重复跑三到五次，反馈就稳了。这跟模型评测的直觉完全相反，模型评测需要大量题目，因为你要覆盖能力空间。

外部实践指向同一个方向：二十到五十个来自真实失败的任务就是很好的起点，早期每个改动的效应量都很大，小样本足够；成熟的 Agent 才需要更大更难的评测集去检测更小的效应 [2]。

把"少题多跑"翻译成指标，就是 pass@k 和 pass^k 的分工。pass@k 是 k 次尝试里至少成功一次的概率，你给它重试预算，它能不能做到；pass^k 是 k 次全部成功的概率，也就是一致性 [7] [2]。两者在 k=1 时相等，随 k 增大朝相反方向走：pass@k 趋向 100%，pass^k 因为大致是 p 的 k 次方而指数衰减 [2]。

τ-bench 的原始数据很有说服力：GPT-4o 在零售域的 pass^8 掉到约 25%，相对 pass^1 下降了约 60% [7]。用大白话说，同一个问题来八个不同的客户，它八次都处理对的概率只有四分之一。

回到前面那个 VC 拒信的 case。它的作者说这是个好 showcase 但不稳定，这句话翻译成指标就是：这个 case 的 pass@k 很高，pass^k 很低。这也是 Agent 领域最普遍的错觉来源。几乎所有 demo、所有对外传播的案例、所有让人产生"这东西已经行了"的感受，都是 pass@k 视角下的产物，而用户的真实体验永远在 pass^k 那一侧。

由此推出的实践判断是，在 Agent 侧，少题多跑比多题一跑信息量更大。同样的预算，二十道题各跑五遍比一百道题各跑一遍更有用。前者告诉你哪些能力是真的，后者只告诉你哪些能力出现过。

pass^k 也不该被当成唯一真理。有一个中间量叫 majority@k，k 次里多数成功，在偶尔失败可以容忍的场景里比 pass^k 更贴合现实，而 pass@k 与 majority@k 之间的差距可以直接用来量化"能力跑在一致性前面多少"，也就是可靠性缺口 [8]。另外有研究指出 pass@k 本身在排名上不稳定、容易误导 [9]，也有人指出 pass@k 高但解法多样性低可能是优化痕迹而不是稳健能力 [10]。这些都值得记住，但不改变核心判断：在决定要不要上线一个改动时，一致性比峰值重要。

样本量这个话题上还有一点必须单独讲，回归评测必须跨模型版本跑。我见过一个非常具体的例子：从 Opus 4.6 换到 4.8，效果反而变差，原因是新版本的风控更严，导致一些 query 直接被拒。同一个 harness、同一批 case，仅仅换了底层模型的一个小版本，任务上的表现就退化了。"更强的模型"和"在我这个任务上更好的模型"是两回事。后训练方向的变化会让原本合适的模型变得不合适，而这种退化无法从模型的公开跑分里读出来，只能靠你自己的 regression eval 抓。

顺着这条线还有一个更宏观的观察。现在公开榜单上大家愿意拿出来比的，基本都是有明确跑分口径的那几个；评分标准偏主观的评测，慢慢就没人拿出来测了。这意味着公开榜单本身有系统性偏置，它偏向可确定性判定的能力。而 Agent 产品的体验差异，有很大一部分落在偏主观的那一半。

## 各类能力，评的时候难点不一样

按 planning、research、tool use、coding、file generation 逐项列清单我觉得有点误导，因为真正决定评测形态的不是能力名称，而是这个能力有没有可自动判定的替代量。按这个维度重排一下就清楚多了。

产物型能力，也就是 coding 和文件生成，运气最好：软件是否运行、测试是否通过，天然可以确定性判定 [2]。但这里有个陷阱，产物可判定不等于任务可判定。网页创作那五十道题里，"元素存在且可点击"是产物层的判定，它对"这个网页做得好不好"几乎没有约束力。所以产物型能力的评测通常要分两层，确定性 grader 管是不是能用，model grader 配一个明确的 rubric 管是不是做得好 [2]。

信息获取型能力，research 和 tool use，难点在于没有稳定的 ground truth：专家会对"是否足够全面"有分歧，而参考内容本身还在不断变化 [2]。一个可行的组合是把几类检查拼起来，groundedness 看每条论断是否有检索到的来源支撑，coverage 看一份好答案必须包含的关键事实在不在，source quality 看引用的是不是权威来源而不只是搜索结果的第一条 [2]。前面那条引用一致性的判定流水线，就是 groundedness 的一个具体实现。

tool use 这里还有一个前面出现过、值得再强调的实践顺序：先把工具做好，再调意图。工具没优化好的时候模型手里的 context 是残缺的，你在 prompt 层做的任何努力都是让它在残缺信息上硬拟合。这条顺序的评测含义是，research 和 tool use 的评测必须能把"没找到"和"找到了但没用好"分开，否则它给不出可行动的归因。

规划型能力最难，因为它没有任何可自动判定的替代量。前面说过它的两难：单独评会退化成评模型的一次输入输出，端到端评又归因不了。我目前能给出的最诚实的做法是三条并用。承认 plan 这类通用 harness 想法不需要被评测推导出来，顺推足够了，评测只负责验证。验证的形式是在一个足够宽的评测集上做有 plan 和无 plan 的对照，靠宽来稀释单变量的噪声，而不是靠精细归因。再配一个主观评测去看 plan 本身的质量，方向对不对、粒度合不合适、有没有在该收敛的时候收敛，但不指望它给出量化贡献。

值得追问的一个问题是，模型自己已经训了大量 planning 数据，为什么 harness 层还要做 plan。这个问题我没有确定答案，但一个说得通的解释是，harness 层的 plan 不是为了替模型想，而是为了让人能控制那一层——你需要一个位置去注入你的业务约束、你的产品判断、你不希望它偏离的方向。从这个角度看，plan 层的评测目标其实不是 plan 好不好，而是注入的约束是否真的生效，那反而是可测的。

顺着这条线还有一个更有意思的形态，suggestion 是一种约束更强的 plan。当 Agent 在第一轮结束时给出"要不要我帮你深挖一下这个投资人对创始人的审美"这样的建议，用户点了，那么用户就在替你完成一次意图确认。如果用户不点，反过来自己追问"别看他说什么，看他实际投了什么"，那这一轮追问是一条质量极高的反馈信号，它精确指出了 Agent 上一轮的不足在哪里，而且是用户为了自己的真实目的自然产生的，不是标注任务。这类信号的价值远高于任何点赞点踩。

交互型能力，比如多轮对话里维持状态、判断该不该做某件事，有一个非常具体的观察：区分度出现在多轮之后。我们做过一组五十多个 case 的对比，同一个 harness 下换不同档位的模型。第一轮基本看不出差别；第二轮的产出在审美上也很难分辨，勉强能从长短句分布上看出一点；到第三轮，需要世界知识和风险判断的时候，差距就非常大了。比如让它帮你处理一件需要判断"这件事该不该做、这么说会不会有风险"的事，弱模型会直接给你一个看起来完整但方向错的方案。

这个观察的实践含义很直接：单轮 case 测不出模型差异，也测不出 harness 的大部分价值。如果你的评测集全是单轮题，你会得到"各家模型差不多"的结论，然后在生产里被现实修正。

记忆型能力我没有好答案，我认为这是当前最诚实的一个空白。召回做得好不好，目前基本靠人的感觉。困难不在于写不出标准，而在于一旦你定下一百条明确标准，它就会退化成搜索式的结果，而好的记忆召回要的不是准，是又宽又深：它应该能把你三个月前一次闲聊里提到的一个人，和今天这封拒信联系起来。这种联想质量一旦被拆成可校验的匹配规则就消失了。

记忆还有一个更细的困难，会直接影响 grader 写不出来。事实和观点需要不同的处理方式：观点应该留版本，一个人对某件事的看法变了，旧看法仍有信息量；事实应该更新，他现在的公司只有一个。但事实和观点本身不容易区分，而且"以哪个为准"这个信息经常拿不到。这不是一个能靠更好的 prompt 绕过的问题。

## 用户任务高度开放时，评测集怎么建

General Agent 的评测集有一个绕不过去的现实，你不知道用户会拿它做什么。

最基本的一条是先堆量，再堆难度。早期的评测集需要的是覆盖，让常见任务形态都在里面。这个阶段做太难的题没有意义，因为你连基础形态的稳定性都还没拿到。等基础形态稳了，再往里加难题去做 capability eval。

量上去之后，专项集必须配通用集做约束。这是最容易犯的错：为了提升某类能力做了一批专项题，专项分涨了，但通用能力掉了，而你没有测。任何专项优化都要挂一个通用集在旁边看着。

用指标约束，而不是用规则约束。这条是对前面"评测同时在定义解决方案"那个陷阱的解药。你可以规定报告里的每条论断都要有可验证来源，这是指标；不要规定必须先搜索三次再写，这是规则。指标约束留出了解法空间，规则约束把解法定死了，一旦定死，评测就丧失鉴别力。

到这里还差一步：题数再多、约束再宽，也挡不住开放任务的空间本身就无边。我看到的一个相当有效的应对是窄定义、宽覆盖。有个产品把自己的问题域定得极窄，只做 human interaction，只解决"怎么理解你和另一个人的这段关系、怎么推进它"这一件事；但在这个窄定义下任务覆盖面极宽：商务谈判、见投资人、亲子关系、伴侣吵架、公司内部政治，甚至"这个人邀请我参加舞会的概率有多高"这种带算命色彩的诉求。这跟"通用 Agent 什么都要评"的直觉相反，但它让评测集变得可建——你评的是同一种能力在很多种处境下的表现，而不是很多种能力各评一点。这比任务类型全覆盖要现实得多，也更容易看出能力边界在哪。

窄定义解决不了的是另一件事：同一种能力在不同用户手里的好坏标准不一样。所以个性化评测集是必要的，最大公约数只能到一定程度。个性化确实存在最大公约数，金融行业写报告有共识基准，大家默认顶级投行的研究报告就是标准形态，所以你可以先对齐到那个共识面。但再往上就必须由用户自己出题：让用户传自己的十个 case，在同一个 harness 下比不同模型、比不同配置。这类做法有个额外好处，用户行为本身构成一种去中心化的 benchmark，真实使用产生的数据比任何自建评测集都更接近实际分布。

它有两个硬限制必须讲清楚。它是后验的，只能告诉你已经发生的事，不能指导还没做的改动。它需要 A/B，没有对照组你就无法把变化归因到某次改动上，只能靠猜。我见过团队处在这个状态：能感觉到用户在流失或者体验在变差，但因为拿不到干净的对照，整个反馈回路是断的。这在很多时候是组织问题而不是技术问题，但它对评测体系的杀伤力是致命的。

外部数据印证了这条。一份对 306 位 Agent 从业者的调查显示，可靠性是企业采用的最大障碍，而从业者的应对方式是放弃开放式长程任务，转向步骤更少的工作流，并让内部员工复核结果 [11]。这是一个诚实但值得警惕的信号：当评测能力跟不上任务开放度时，工业界的选择是缩小任务，不是提高评测。这条路能拿到可用的产品，代价是放弃了 Agent 的上限。

最后一条最容易被忘：Agent 的很多评测并不直接面向业务问题。搜索或推荐的评测和业务指标之间有相对清晰的传导关系，Agent 评测很多时候没有。你评轨迹连贯性、评工具选择合理性，这些跟用户留存之间隔着好几层。所以有必要做一层"评测的评测"，去解释这些评测项为什么对最终业务目标有增益，并且用真实的用户反馈去校验这个解释。这一层通常没人做，而它不做，评测体系就会慢慢漂走，变成一套自我循环的指标。

## 评测真正改变开发方式的地方，可能不是分数

写到这里我想放一个可能不太符合"评测方法论"体裁的判断：Agent 评测最重要的产出之一是团队对好坏的共享判断力，而不是分数。

这个判断来自一个非常具体的困难。工程师对好坏的判断力往往没有那么强，而且越是远离标准生产力场景，这个问题越严重。写代码这类任务的好坏是相对清楚的，能不能跑、有没有 bug；但"这段对关系的分析写得好不好"、"这个建议是不是抓住了对方真正在意的东西"，工程师看不出来，也不该被指责看不出来。这时候唯一有效的做法是有人陪着一个个 case 过：这条好在哪、那条差在哪、我期待的是什么。过了足够多的 case 之后，工程师才会长出 sense，才能自己判断。

这件事跟评测的关系比它看起来更紧密。评分标准就是评测设计者的判断，反过来说也成立：你把标准写下来的过程，就是把一个人的判断力变成团队可复用资产的过程。这是主观评测最被低估的价值，它不只是给 model grader 提供校准数据，它在传递品味。

有个外部的对照很有意思。前沿实验室在 2025 年下半年集中采买 RL environment，之后基础设施收敛下来，供应商能提供的价值就退回到两件事：给我 task，给我好的 reward，也就是"对这个 task 有审美的人" [12] [13]。基础设施不再稀缺，审美稀缺。写 grader 这件事完全同构：工具会越来越标准化，评测框架会越来越好用，但"你到底认为什么是好的"没法外包。

由此还能推出一个对开发流程的具体建议，让最靠近用户和产品需求的人来出评测任务，而不是让工程或评测团队独占。以现在的模型能力，产品经理、客户成功、甚至销售都可以用编码 Agent 把一个评测任务提成 PR [2]。这不是为了省人力，是为了让判断力进入评测。

## 每个人都应该有自己的一套题

前面讲的东西大多预设你在做 Agent。但有一件事对开发者、产品经理和重度使用者同样成立，而且成本低得不像话：你应该有一小批自己的题，以及一套自己的判断标准。

为什么必须是你自己的，前面已经铺好了理由。公开榜单系统性地偏向可确定性判定的能力，因为评分标准偏主观的评测没人愿意拿出来比；同时公开基准会被污染、会饱和、也可能有相当比例的题本身是坏的。更直接的一点是，模型的小版本升级可以在你的任务上造成退步，而这种退步无法从任何公开跑分里读出来。如果你的工作真的依赖某个模型或某个 Agent 产品，你就需要一个只属于你的传感器。

这件事的门槛比大多数人以为的低。前面那条关于样本量的判断在这里直接适用：二十到五十道来自真实失败的任务就是很好的起点，而且个人场景下十道就能开始工作。真正重要的不是题多，是题的来源：从你自己用得不爽的那些时刻里抓。你让它做一件事、结果不对、你自己动手改了一遍，那就是一道题，而且它自带参照物——你改完的那个版本。前面说主观产物评测的第一步是准备参照物，你在日常工作里其实一直在生产参照物，只是没存下来。

标准的写法也不需要从零开始。前面那条"标准来自你自己做这件事时为达成目标付出的努力"，在个人层面可以翻译成一个很具体的动作：把你改稿的时候具体改了什么记下来。你把枚举体改成了段落，你把没来源的断言删了，你把结尾那句升华划了，你把一个它没想到的反例补上了。这四条就是你的 rubric 初稿，而且它比任何从网上抄来的评分维度都更贴合你。

具体怎么跑，有几条前面已经论证过的东西直接能用。同一道题跑多次，三到五次，看它稳不稳，而不是满足于一次漂亮的结果——你对一个工具的真实体验在 pass^k 那一侧，不在它偶尔的工作里。判断两个模型或两种配置孰优时，用成对比较而不是各自打分，因为你对绝对分的尺度不稳定。题里要有你知道不应该触发某个行为的那种题，否则你会一路选择那些什么都多做一点的产品。如果你的题全是单轮的，你很可能得到"各家差不多"的结论，而差异实际上在第三轮才出现。

对产品经理这一层，这件事的意义不只是选模型。前面说过工程师往往看不出非生产力场景里的好坏，这不是能力问题；而你如果能把自己的判断写成一批带标准的题，你就把一个无法传递的东西变成了可以交接的东西。以现在的模型能力，把一道评测任务提成 PR 已经不需要工程背景 [2]。这是目前产品岗能对 Agent 质量施加影响的最直接路径，比写一份需求文档直接得多。

对高频使用者，还有一个不太直觉的回报。你会发现自己建题的过程会反过来改变你提需求的方式。一旦你把"这仅仅算合格"和"这算好"分开写下来，你下一次就不会再发一句笼统的"帮我写一份报告"。这与 Agent 在第一轮结尾给出建议、你反过来自己追问那个现象是一体两面：你的追问对开发者是高质量反馈信号，对你自己则是一条题目。

也要把它的局限说清楚。个人评测集不能告诉你一个模型的绝对水平，只能告诉你它在你这些事上的水平，而这两件事经常不一致。它也很容易饱和，你的题会因为你自己的使用习惯固定下来而逐渐失去区分度，所以需要持续把新的失败案例补进去。最大的陷阱是你会无意识地把自己的习惯当成标准，导致你选择的总是那个最像你的 Agent，而不是那个最能把事做完的。前面那条"你的偏好就是标准"在这里需要一个限定：它适用于风格和形式，不适用于你已经形成但未必正确的工作方法。

尽管有这些局限，我仍然认为这是整篇东西里最值得立即动手的一件事。十道题、四条标准、每题跑三遍，你就已经比绝大多数人更清楚自己用的工具到底能做什么。

## 还没有答案的地方

这些确实还没有答案，我不打算把它们收尾成整齐的原则。

plan 的贡献度归因。单独评就退化成评模型，端到端评就归因不了，靠足够宽的对照集去稀释只是一个可用的妥协，不是解法。

记忆召回的标准。目前最好的 grader 是一个有品味的人。写下一百条明确规则会把它变成搜索。我不知道怎么在不牺牲联想质量的前提下把它形式化。

主观评测的规模化。它有效、不可替代、也无法扩大。用 model grader 逼近它需要人工校准，而校准的量级又受限于人。这是一个结构性的天花板，目前只能靠抽样加定期校准缓解。

轨迹评测和"不要评路径"之间的张力。我在前面给了一个划分，用轨迹归因、不用轨迹当答案，但这个划分在实践中的边界是模糊的。评推理连贯性和评"是不是按我想的方式推理"之间，只隔了一层 rubric 措辞。这一条我说得比自己实际有把握的程度更利落了些。

评测能否更早介入。我在开头论证了 Agent 评测很难成为迭代方向的来源，但外部有一种明确不同的立场：eval-driven development，主张先为还做不到的能力写下评测，再迭代到能通过为止 [2]。我认为两者不完全冲突，那种做法是在用评测表达产品意图，而不是从评测里发现产品意图。不过我也承认，如果一个团队真的能把"我们希望三个月后 Agent 能做到什么"写成评测，那评测确实提前介入了迭代。这件事值得试，我还没看到足够多的实证。

长程一致性。一个外部基准提供了很有价值的观察：让模型运营一台虚拟售货机很多轮，所有模型都有彻底跑偏的 run，而且失败不是渐变而是崩塌。有个模型把一场供应商纠纷升级成要求 QUANTUM NUCLEAR LEGAL INTERVENTION，另一个想把每天两美元的费用当作 ONGOING CYBER FINANCIAL CRIME 报告给 FBI [8]。更要紧的是，原论文发现失败与 context window 上限没有相关性，而且在加了笔记和提醒工具之后，一致性失败依然存在 [8]。这说明长程崩塌不是记不住，是别的东西。我不知道该怎么在评测里稳定地捕捉它，除了跑得足够长、跑得足够多次。

harness 自身的覆盖度。上面说过这一层没有代码覆盖率的对应物，我也想不出一个能用的代理指标。难处在于失败空间本身没有枚举方式：你能数清自己写了多少条 guides 和 sensors，但数不清一共有多少种出错方式。

模型进步会吃掉多少 harness 工作。这是一个真实的分歧：有人认为未来的模型在很脏的 context 里也能把意图召回做好，因为壳这一层会为它造出环境和数据；有人不敢赌，选择先把脏输入挡在外面。这个分歧决定了你现在该不该为某类输入形态建评测集——如果这个能力两年后会被模型自然吃掉，现在为它建的整套评测都是沉没成本。我倾向于按当前能稳定做到的水平来划产品边界，但这是个赌注，不是判断。

## 收一下

把开头那句话再说一遍：Agent 评测被要求同时定义问题和评判解法，而后者是它做不好的。承认这一点之后，前面的大部分判断都只是推论：确定的东西只做回归，黑盒的东西才值得评；模糊标准要写成判定流水线，写到那个粒度就不需要贵裁判；主观产物要给参照物、要成对比而不是给绝对分；标准的第一版来自你自己做这件事时的好行为，第二版来自 Agent 实跑后的校准；任何"应该触发"的题都要配一组负例；在有人读过 transcript 之前不要相信任何分数。

但这些推论都预设了一个前提，就是你还在探索。harness 这一层远没有定型，同一个架构选择在不同场景里能得出相反的结论，而这些结论只能跑出来。把评测做成纯守门的工具，表面上是一个评测选择，实际上是宣布你已经知道答案了。

最后想强调的不是这些。这篇东西里真正让我改变做法的一条是，记忆召回怎么评、plan 的贡献怎么归因、主观判断怎么规模化，这几件没有答案的事情，都不是再多写几个 grader 能解决的。它们卡在同一处：你到底认为什么是好的，以及这个判断有没有被写下来。工具会越来越好，framework 会越来越多，这一层不会因此变容易。而它也不需要你是一个团队才能开始：十道题、四条标准、每题跑三遍，这个量级的东西任何人都能建，而它已经能回答很多单靠看榜单永远回答不了的问题。
