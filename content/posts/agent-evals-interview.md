## 为什么需要 Agent 评测

**Kaiyi**：为什么要做评测？因为 Agent 这个东西，你对它的改动是有不确定性的。它依赖模型的随机输出，所以得有一些评测。有些东西不是说你做了逻辑 A，就一定能产出逻辑 B。

你在改一个东西的时候，它的耦合性非常强。比如你改了第一句 prompt，可能就会对最后一句 prompt 的结果有影响。这对人来说是比较黑盒的。虽然它有一定程度的逻辑，相比于训练模型也有一定程度的可控性，但让人把它的逻辑完全梳理清楚，是一件太困难的事情。所以相比于正常软件开发里的测试，评测的重要性会被提上来。

**沐秋**：我之前发了你两个问题，你觉得那两个怎么办？什么叫“模型评测只定义问题，Agent 的评测还要定义解决方案”？

**Kaiyi**：模型评测很多时候是基于已经调好的算法、训练架构，往里面加数据。那个领域的问题很宽泛，你出一些特别符合人类直觉的问题，去指导“我们的模型应该发挥出这个效果”。但根据一个评测，再去想除了数据之外的解决方案，其实没有那么容易。

模型评测比较通的路径是：先定义问题，定好问题之后，通过数据去解决。因为大家的算法、后训练范式、预训练范式已经定了，所以你要想的解决方案，可能就是去哪采买数据。对于怎么实现、代码怎么改，大部分模型评测应该不会直接告诉你。

另一种模型评测，比如 GAIA 或者 HLE，只是把问题抛出来：人类社会中有这样的问题。至于模型怎么解决，它不管。

之前 Manus 跟你聊的东西，应该也有类似的感觉。比如隐喻类的问题，把这个问题抛出来，但你能干涉的方案，要么少用一点这种数据，要么微调时给类似的数据，不要用这种形式去打标。模型评测是这样的。

**沐秋**：听起来，模型评测目前这个阶段只需要数据就能解决所有问题吗？

**Kaiyi**：不是所有问题。模型发展过程中，必然有很多问题没办法通过数据解决。模型有三驾马车：算法、数据和算力。但现在大部分被排到台面上的问题，都是依赖数据去解决的。

你看这两天那个 GAV 模型，以及各种 researcher、群友提出的模型训练范式，并没有看到那些训练范式对我们实际使用的模型产生什么影响。一方面是它面对的问题没有那么直观，另一方面是现在通过数据去大力出奇迹，就可以解决很多问题、达到很多效果。这是现在模型评测的主要情况。

## Agent 评测与产品设计

**Kaiyi** Agent 的评测不一样，因为里面还有很多要干涉的东西。Agent 很多时候是一个产品表现的东西。我们有时候不得不承认，Agent 不是像模型一样，只要造出来就会有人用，它要面向人去使用。

用户用模型的时候，不一定会很直白地说“它会这个，不会那个”。大家可能模糊地评论一下，或者带着自己先入为主的印象去评论模型能力。但对 Agent 的喜好、偏好是更明显的。

一方面，现在会用 Agent 的人偏 early adopter，所以大家更较真。另一方面，搭一个 Agent 的时候，很多东西是由你自己完全理解的一行 prompt，或者一行代码去驱动的。它建立在模型之上，就多出了很多基于模型的产品设计。

比如 Codex，不管什么问题，它都特别喜欢写代码去解决。调研问题有时候也写代码，绘画类或者其他复杂一点的问题，也会写代码去解决，并且把代码的技术方案告诉你。这就是它的一项产品设计。

Claude Code 最开始也是这样，现在删了很多那个东西。后来又拆出了 ChatGPT Work、ChatGPT 网页版的 Pro 模式，还有 Claude Cowork、Claude Design，各种各样的产品，每一个都是一个 Agent，里面都有它的产品设计。

这些产品设计，不像以前写代码，写好了之后行为基本就确定了。它不确定的地方相对更多，模型又引入了一些随机性。有些 Agent，比如 Manus，主要的产品呈现点就是把模型能力展示出来，这会把测试的重要性抬高。

大家完全依赖固定代码逻辑去完成功能的时候，很多人最后自己就不测了，或者自己摸一下、交给外包测试测一下就得了，不会那么关注一定要评测一下，保证条条框框都靠谱。

Agent 不行。不管小公司还是大公司，都有这种现象。小公司可能一定要找一个非常负责的人来做 Agent，他要了解整个 Agent 的行为，了解每个行为是由模型的什么特性，或者自己的什么改动导致的，才能做出比较好的 Agent。

大公司能看到的现象是，有些 Agent 工程师觉得做一个改动非常麻烦，不愿意改，会逃避去改。因为这跟写代码的区别在于：你改一个东西，也不知道结果，需要费很多脑子，或者经过相对复杂的评测过程，去保证改动有效。

所以在 Codebuddy、Workbuddy 等一些 Agent 产品里，能看到很差的行为。Workbuddy 比较明显，比如很简单的做 PPT 的事，它的效果比 Gamma 差，比 Gamma 贵，还要三十多分钟，Gamma 五分钟就做完了。这是 Agent 需要评测这件事情，在组织里反馈出来的一些现象。

**沐秋**：我可以理解为，你觉得目前这个阶段，或者以后很长一段时间，Agent 评测就是修 bug，跟软件领域修 bug 是一样的吗？

**Kaiyi**：我觉得 Agent 评测的出发点，跟软件里修 bug 是一样的，本质是一样的。只不过大家对软件非常了解，软件确实也是一个确定性的东西。你改 A，B 不会出现影响，这件事情是确定的，所以软件测试没有被放到如此重要的地位。

但 Agent 一方面有负责程度的问题，另一方面有现在代码框架、大家共识程度的问题。比如很多人研究 Agent harness，完全是为了解决自己做出的负优化。实际上 Agent harness 可以非常简单，只不过大家搞不懂这个事情。

你现在看到很多校招生面 Agent 工程师，刷的八股文题目还是“如何用 Coze 搭建一个智能体”。我们都知道，Coze 前两天已经被全部裁掉了。这个技术还很新，业界没有形成什么共识，所以会有这些现象。

**沐秋**：所以你现在很多工作要做 Agent 评测吗？

**Kaiyi**：我之前做，但现在因为合作不太顺畅，也不做了。

**沐秋**：但理论上每家都得有人做，对吧？

**Kaiyi**：我觉得是。大公司肯定会抛出这个职责，让一个人跟进。小公司，比如 Manus，宁可自己拿那些常测的题去看这个东西的手感正不正常，这也是一种评测。

**沐秋**：你觉得像 Manus 这种公司，理论上更应该很重地去做 Agent 评测吗？

**Kaiyi**：重和不重有两种程度，一种是思维负担和上心程度，另一种是人力安排程度。

Manus 的 Agent 做得好，是因为他们对这个事情的上心程度，他们在这件事情上投入的思维负担非常多。你想，他们有两个联合创始人级别的人，每天在那里调 Agent 的效果，其他联合创始人也每天用那个东西、给意见。

他们有一个比较高素质、名校毕业的人才团队，去做更外部视角的评测，每天想各种实际问题抛出来，然后写一份报告。虽然这个东西不一定对结果有什么直接指导，但报告也有参考价值。

**沐秋**：所以你觉得，他们是在很重地做 Agent 评测。

**Kaiyi**：我觉得大家甚至不要把评测当成一个那么独立的领域，或者把它看成一个原子性的概念。你说 Manus 非常上心地做评测，也没有问题。但更大白话的说法是，Manus 这家公司对自己的 Agent 效果，对自己想让 Agent 呈现出什么样的效果，非常负责、非常上心。

## 评测难度与迭代

**沐秋**：测模型和测 Agent，哪个难度更高一点？你觉得是测 Agent 的难度更高一些？

**Kaiyi**：目前这个阶段，我觉得测 Agent 的难度更高。如果有一天模型在现在这种暴力给数据的情况下卡住了，那测模型的难度也可能更高。

**沐秋**：因为目前遇到的模型问题只有数据，所以测模型还好？

**Kaiyi**：不是模型的问题只有数据，而是依靠现有训练范式，以及在数据上做工作，可以解决很多问题、见效。有很多问题是数据解决不了的，确实需要算法提升，但现在那些提升没有做数据工作来得大。这也是为什么大家喜欢蒸馏，国内的模型都喜欢蒸馏。

**沐秋**：那抄别人的 Agent 框架不可行吗？比如 Workbuddy 抄千问办公，千问办公抄汇报工作，或者它们都抄 CC，有那么大难度吗？

**Kaiyi**：我觉得抄没有那么大难度，搭一个自己可用的完全可行。都不用抄那些，把那个 coding agent 拷贝下来，里面没有多少行代码。我印象里，它的 system prompt、工具描述之类的，加起来可能一两千行字。

这是很简单的事情。一个人一下午可能不能完全理解里面的思想，但至少可以讲明白里面有什么东西。

实际业务跑起来的时候，你会收到用户各种各样的反馈，每个人都会对 Agent 有各种效果上的要求。抄了之后，你得懂里面有什么，还得懂怎么改，又得有评测。不能抄过来就完全不变了。

**沐秋**：主要是迭代的问题。

**Kaiyi**：主要是迭代。评测就是服务于迭代的。

## 模型会吃掉 Harness 吗

**沐秋**：模型最后能吃掉 harness 吗？模型能力更好了，测那些是不是区别不大？或者上一个新模型要做适配吗？不同模型用一样的 harness，适配有什么讲究？

**Kaiyi**：Harness 里面有些东西肯定要做适配，比如 plan。现在所有模型训练的数据里，都有先做 plan、再执行这一步，所以现在改成有 plan 的，一定比没有 plan 的好。

这个话题还有一个类似的事情：之前很多人讨论，什么样的产品会被模型吞噬。模型后面解决的很多问题，也是产品问题。

比如视频模型的分镜。以前各种视频创作工具，可能有自己的方法去解决分镜问题，但这个问题也能被模型通过训练一些数据来解决，那之前大家雕的那些花就没有用了。这是会被吞噬的一部分。之前服务于怎么做分镜的那些东西，也算视频 Agent harness 的一部分。

但有些东西不一定会这样，或者迟迟没有达成共识。比如 Manus 一个很明显的现象是，稍微复杂一点的问题，给你的结论里极大概率一定有一篇文件，放一个稿子在那里。

这个东西没有达成共识，有些人喜欢，有些人不喜欢，所以不一定会被训进模型里，训进模型里也不一定能解决所有人的问题。可能有一些模型会有这种倾向，复杂一点的问题直接给一个文件，但不是每个模型都有这种共识、都有这种能力，那也说不上它被模型吞噬了。

模型会衍生出很多新行为，会加很多新数据，有些东西会被覆盖掉，比如分镜能力；有些东西也可能因为大家觉得这种效果好，又把它加上。

举一个最极端、最直观的例子：创作一篇长文。直接让模型一把梭吐出来，行不行？可能可以。但现在的范式都是先让模型规划一下，写第一段、第二段、第三段，最后合在一起。

模型不能直接稳定地输出一篇长文，于是选择降级，先拆分任务，再用工具分别处理，然后总结、合在一起。这反而是模型的训练方式上面长出了 harness。

我觉得所有围绕模型的工作，包括 harness，都有一个比较核心的目的。现在引入一些概念，可能是一个不太好的事。

刚才引入了评测的概念，但很多人太计较评测应该怎么做，忽视了评测是在为自己的 Agent 效果、为自己想让 Agent 产出的效果负责。很多人通过这个词、这一层概念，屏蔽了后面真正应该做的事。

Harness、context engineering、prompt engineering 这些词，也可能屏蔽了我们真正跟模型打交道的目的。开发者或者产品负责人，是希望模型表现出我们想要它有的表现，输出我们想要的结果，行为符合我们的产品定义。所有做 prompt engineering、harness、context engineering 的目的都是这个。

## 运行过程应该怎么评

**沐秋**：你主要是觉得现在大家的方向不太对吗？

**Kaiyi**：我没有觉得方向不太对，我只是说，我对这个事情的认知框架是这样的。

客观来说，确实有些公司、组织的探索方向有明显问题。因为这件事情没有特别明确的主线，也没有已经形成共识的路径，告诉大家应该从 A 做到 B，每一步应该怎么样。大家都还在探索阶段。

确实有些方法是错的。我觉得应该有一些基本的 mindset，大家抱着探索的目的，去搞好每一步应该怎么做。

Agent 评测还有一个难点。刚才提到的评测指标，都非常面向用户最后的使用结果。但我不确定 Agent 以后会不会成为一个端到端的东西。我觉得，如果还是现在这种方式，它可能不会成为一个完全端到端的东西。会持续有一部分用户，或者所有用户在一部分时刻，需要查看 Agent 的运行过程。

要查看运行过程，就会面临另一个问题：有些评测指标不能直接根据产品问题定义，还要想什么样的表现是好的、什么样的中间过程是好的。这相对有点难，因为它不是直接服务于业务场景的。

这有点像做一把钳子，你要研究钳子中间那颗螺丝，什么样的情况是好的。这类问题目前还没有比较良好的定义形式。

直接定义一篇文章的产出风格，或者视频的产出风格，有很多资料可以从里面发掘建立评测指标的灵感。但评中间过程，应该所有人都知道要去评，难点是它没有直接的产品问题那么容易发掘评测指标。

**沐秋**：除了 Manus，还有谁在认真做评测？我感觉没怎么听说过千问办公它们在做 Agent 评测。

**Kaiyi**：大公司的经验可能不是那么好复刻。我印象里，业界比较权威的评测资料分享，还是 OpenAI 和 Anthropic。

另一个问题是，评测涉及你的产品定义，把它完全公开出来，有时候商业上也不太能做。

再就是，我们刚才说，看起来可行的方案是要对自己做的效果、做的东西非常负责，大公司很难找出一个人非常负责。

## 换模型与适配

**沐秋**：做 Agent 评测的时候，你会换模型，还是固定一个模型？

**Kaiyi**：模型肯定要换着测，不可能绑定在一个模型上。有些行为，换个模型可能就有了，你还要决定要不要适配，或者把那个行为去掉。

这种听起来就很恶心，没有什么定数，看起来只能凭个人感觉。

**沐秋**：不然变量也太多了。

**Kaiyi**：参考 Manus，他们觉得文章写得很长是好的，最后给一篇文件作为交互是好的，这都是自己的定义。

换模型后，有些模型表现不出这种行为，就得调；有些模型表现出了特别好的行为，就用。

**沐秋**：他们先定一套，最后让所有模型适配到那套东西里。

**Kaiyi**：是。他定义这个是好的，就这样做。或者有些模型跑起来后，发现那个效果也不错，要不都对齐那个效果，或者索性对那个模型不调了，也都可以。

**沐秋**：这事情真是没完没了。

**Kaiyi**：这是一个产品问题，是一个产研结合的问题。一定要有一个产研结合的人，对它非常负责，而且能推动这个事情去改。

另一个是，很多时候要跑起来才知道效果，里面的耦合又特别多。你改一个东西对另一个东西的影响，心里得有数。一切都回到非常负责这件事情上，但非常负责是一个很难的要求。

**沐秋**：比如你之前的工作是让 Tabbit 的 Agent 效果变好，理论上是不是要把你们接的所有模型都测一遍？

**Kaiyi**：要测，所有模型都要测。Manus 就是全都测。卫衣写的文章里也说了，针对那一个指标，所有模型都测了一遍。

**沐秋**：那你呢？

**Kaiyi**：我这边就别提了，没什么力量推动。

**沐秋**：卫衣好像也就一到两个人在做。

**Kaiyi**：我记得应该是卫衣，还有一两个人，再加上 Peak 本身，还有一个叫范斌的人。他们几个人做得非常棒。

## 自有模型与商业决策

**沐秋**：假设一下，千问办公和豆包工作今天的状态，是不是在你看来更 make sense 了？因为它们只用自己的模型，理论上适配能做得更好，评测会做得更少，也会更适应。不开放用户选模型，是不是一个好的事情？

**Kaiyi**：我不确定。因为调 Agent 效果，还有一个手段：不仅能改 history，还可以让模型重新训练，微调模型。

我觉得对它们来说，这是一个公司战略问题。公司的定位就是所有东西先自己搞。如果有一天模型这一层真的没什么价值了，可能也会放弃自己搞。但至少现在模型这一层，至少在股价上还是有很大价值的。

**沐秋**：那 Workbuddy 呢？理论上它会每一个模型都去适配吗？

**Kaiyi**：Workbuddy 那个模型太差了。

**沐秋**：我是说，理论上 Workbuddy 可以接其他模型，或者用 API 调用。难道它都会适配吗？

**Kaiyi**：至少可能先在组织内看一眼效果，可能有个评估机制。但适不适配，取决于其他各种权衡。

比如有一天 DeepSeek V5 发布了，全网都说特别好，但在 Workbuddy 上，有一个 case 它觉得不通，短时间内工程师、评测师一晚上也调不好效果。这种时候也得硬着头皮上，因为不能错过热度。决策里还会有这些东西。

再举个例子，豆包之前不接别的模型，但在 2025 年初还是接了 DeepSeek，因为热度太高。

大公司的决策涉及的东西比较多。我们主要聊的是怎么把这个事情在技术和产品上做好，但大公司在商业上可能会引入更多要素，那就是另一回事了。

**沐秋**：那现在豆包工作想提升，空间还是挺大的，要做很多 Agent 评测的工作，不仅依赖 Seed 模型进步，对吧？

**Kaiyi**：是。

这里面很多问题是没有结论的。现在很多举措是在纠错、提升人的认知，而不是在把这件事做好上。
